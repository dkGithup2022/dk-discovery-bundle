# 톤 가이드 — 전 문서 공통

이 가이드는 모든 산출물(기획서, 피처 스펙, 페이지 설계, API 스펙, 도메인 모델, 브레인스토밍)에 적용된다.

---

## 원칙

**증거가 말하게 하라. 증거 위에 감상을 얹지 마라.**

---

## 금지 패턴

| 패턴 | 왜 금지인가 | 예시 |
|------|-----------|------|
| "X의 문제는 X가 아니라 Y이다" | 통찰을 연기하는 수사. 그냥 Y를 말하라. | ✗ "도구의 문제는 도구가 아니라 지식이다" → ✓ "패턴 지식이 구조화되지 않았다 (출처: ~)" |
| "핵심 인사이트:", "핵심은 ~이다" | 라벨로 중요성을 강제하는 것. 증거가 좋으면 독자가 안다. | ✗ "핵심 인사이트: 사용자는 조합 방법을 모른다" → ✓ (삭제. 이미 위에서 데이터로 보여줬다) |
| "~해도, ~해도, ~하면 실패한다" | 근거 없는 선언적 단정. | ✗ "노드가 300개여도, 스킬이 강력해도, 모르면 실패한다" → ✓ "CC 스킬 활성화율 ~50% (출처: P0 조사)" |
| 앞에서 데이터로 보여준 것을 뒤에서 덜 정확하게 다시 말하기 | 중복이고 퇴행. 요약하려면 새 관점을 추가하라. | ✗ 테이블로 4개 문제를 보여준 후 "결국 패턴이 없는 것이 문제다" → ✓ (테이블이면 충분. 또는 비교/시사점 추가) |
| 피치덱 톤 | 이건 작업 문서다. 투자자 설득이 아니라 의사결정 지원. | ✗ "혁신적인", "게임체인저", "패러다임 전환", "극대화" |
| 가치 판단 형용사 | 근거 없이 좋고 나쁨을 단정. | ✗ "강력한 생태계", "압도적 성장" → ✓ "183K GitHub stars (2026.04 기준)" |
| 미래 단정 | 예측을 사실로 표현. | ✗ "수요가 폭발할 것이다" → ✓ "수요 증가 가능성이 있으나 미검증 (가설)" |

## 산출물 언어 규칙 — 내부 용어와 압축 조어 금지

워크플로가 정의한 분류 용어(기본기, 차별화, 미검증, 수요측/공급측 근거, 추론 태그,
상위/하위 기획 가설 등)는 **파이프라인 내부용**이다. 사람이 읽는 산출물(기획서, 리뷰 문서,
질문 문구)에서는 그대로 노출하지 말고 보통 사람이 쓰는 문장으로 번역한다.

| 내부 용어 | 산출물에서 쓰는 표현 |
|----------|-------------------|
| 기본기 (카드) | 기본으로 있어야 하는 기능 / 없으면 유저가 떠나는 기능 |
| 수요측 근거 없음 | 유저가 실제로 원한다는 증거는 아직 없다 |
| 추론 태그 / 추론 위에 서 있다 | 아직 확인 안 된 가정이다 |
| 데이터 승격 | 확인된 것으로 본다 (확인 경위 명시) |
| 양면 시장 | 가입자와 운영자 양쪽 |

**압축 조어 금지:** 여러 개의 판단·개념을 새로 만든 명사구 하나에 욱여넣지 않는다.
문제는 명사의 개수가 아니라, **그 표현을 이해하려면 만든 사람의 사고 과정을 되짚어야
한다는 것**이다. 업계에서 통용되는 용어(리텐션, MVP 등)는 길어도 괜찮고, 스스로 발명한
표현은 짧아도 안 된다.
  ✗ "가입 전 판단 결핍의 수요측 언어" — 세 가지 판단(정보가 부족하다 / 유저가 느낀다 /
     그 증거를 찾자)이 한 명사구에 압축되어, 읽는 사람이 해독해야 한다
  ✓ "'가입 전에 판단할 정보가 부족하다'는 불편을 유저가 직접 말한 흔적(후기·커뮤니티 글)"
판별 기준: 이 과정에 참여하지 않은 동료가 그 표현만 보고 뜻을 되묻지 않겠는가.
되물을 것 같으면 판단들을 문장으로 풀어 쓴다. 애매하면 풀어 쓰는 쪽을 택한다.

**허용 경계:**
- 산출물이 자체 용어 정의표를 갖추면, 구조화된 고정 필드(분류:, 근거 수준: 등)에서는
  정의된 용어를 쓸 수 있다. 산문 문장에서는 여전히 풀어 쓴다.
- 프로세스 기록 섹션(Critic 반영 기록 등)에서는 교정 대상 표현을 인용할 수 있다 —
  무엇을 왜 고쳤는지의 기록이기 때문이다.

## 권장 패턴

| 패턴 | 설명 | 예시 |
|------|------|------|
| 사실 → 근거 → 판단(짧게) | 판단은 한 줄. 근거가 본체. | "CC 스킬 활성화율 ~50% (P0 조사). 스킬 구조 개선이 필요하다." |
| "~로 확인되었다(출처)" | 확인된 사실은 출처와 함께. | "커뮤니티 공유 행태가 확인되었다 (GitHub 12K+ repos, P0 조사)" |
| "~는 미검증이다" / "가설" | 모르는 것은 모른다고 쓴다. | "이 조합의 효과는 미검증이다. MVP에서 A/B 테스트로 확인한다." |
| 독자가 결론을 내리게 하라 | 데이터를 주고 판단은 독자에게. | 4개 문제를 테이블로 보여주면, "핵심 인사이트"는 필요 없다. |
| 요약 시 새 관점 추가 | 같은 말 반복 대신, 비교·시사점·다음 질문. | "4개 문제 중 3개는 '실행'이 아닌 '설계' 단계에서 발생한다 → 설계 도구 기회." |
| 수치는 조건과 함께 | 맥락 없는 수치는 오해를 만든다. | ✗ "70% 실패" → ✓ "Latenode(경쟁사) 주장, 방법론 미공개. n8n 커뮤니티 유저 불만은 별도 확인." |

## Critic 적용

reason-protocol의 Critic은 위 금지 패턴을 **MAJOR**로 공격한다.

```
Critic 톤 검증 항목:
  □ 수사적 선언이 있는가 ("X의 문제는 X가 아니라 Y이다")
  □ 강제 라벨링이 있는가 ("핵심 인사이트:", "핵심은 ~이다")
  □ 근거 없는 단정이 있는가 ("~하면 실패한다")
  □ 데이터 중복 요약이 있는가 (앞에서 보여준 것을 뒤에서 반복)
  □ 피치덱 톤이 있는가 ("혁신적", "게임체인저")
  □ 미검증 사항을 사실로 표현하고 있는가
  □ 내부 분류 용어가 산출물 산문에 그대로 노출되는가
  □ 스스로 발명한 압축 조어가 있는가 — 판별은 "참여 안 한 동료가 되묻지 않겠는가" 기준.
    명사 개수 같은 기계적 기준으로 세지 않는다

  위반 발견 시: MAJOR weakness로 등록.
  "증거가 말하게 하라"는 원칙을 인용하여 구체적 문장을 지적.
```
