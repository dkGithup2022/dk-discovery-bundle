# Request Guide Workflow v1 — /dk-discovery-bundle:design-request-guide

디자인 도구(클로드 디자인 등)와의 인계를 6단계로 진행한다. 이 워크플로는 각 단계에서
**첨부할 파일 + 복붙할 프롬프트 + 다음 단계로 넘어가는 확정 기준**을 담은 가이드 문서를 만든다.

원칙:
- 한 단계씩 보낸다. 한 번에 다 던지지 않는다 — 앞 단계의 확정이 뒤 단계의 재료가 된다.
- 구조(스켈레톤)를 색보다 먼저 확정한다 — 구조 결정이 스타일에 오염되지 않게.
- 프롬프트는 완성문으로 조립한다: 기획 문서의 실제 내용(서비스 한 줄, 분위기, 페이지 목록,
  공통 컴포넌트 후보)을 채워 넣는다. 받는 쪽은 우리 파이프라인을 모른다 —
  내부 용어 없이, 문서만 읽고 이해되게. (tone-guide)
- 구조는 우리가 이미 만들었다: 사이트맵 · 유저 흐름 · 와이어프레임. 디자인 도구에는 구조를 새로 짜게 하지 않고,
  우리 와이어프레임을 **다듬게** 한다. 페이지·섹션 번호(P4, P4-3)는 디자인 도구와 주고받는 공용 주소로 끝까지 유지한다.

## 입력

```
필수:
  value-proposal/seed-v2.md — 가치 기획 (서비스 한 줄, 고객군)
  ui-spec/ui-spec.md — 용어, 기능 목록, 전역 분위기
  sitemap/sitemap.md — 페이지 목록, 공통 섹션, 페이지별 섹션 목록
  user-flow/user-flow.md — 흐름 목록, 화면 상태 목록
  wireframe/wireframe.html — 색 없는 와이어프레임 (3단계 첨부물). wireframe.md의 진행 상태가 "전체 확정"이어야 한다
선택:
  design_handoff/references/selection.md + 캡처 — 톤 레퍼런스 (없으면 2단계 "준비 후 진행")
  consistency/handoff.json, consistency/summary.md — 정합성 검사 결과. 없으면 가이드 맨 위에
    "정합성 검사를 거치지 않은 기획"이라고 적는다. 있으면 남은 보류·미결을 아래 "정해야 할 값"에 옮긴다
```

## 정해야 할 값 모으기

```
user-flow.md, wireframe.md, consistency/summary.md에서 "조건 미정"이나 "확인 필요"로 남은 값
(글자 수 제한, 사진 장수, 심사 기한처럼 화면 모양에 영향을 주는 값)을 모은다.
값을 지어내지 않는다. 가이드의 "정해야 할 값" 절에 출처와 함께 목록으로 적고,
어느 단계(3 구조 다듬기 / 5 컴포넌트 / FE 스펙)에서 정할지 표시한다.
```

## 6단계와 프롬프트 틀

각 단계는 가이드에서 다음 형식으로 기술한다:
**목적 / 첨부 파일 / 복붙 프롬프트 / 확정 기준(이게 되면 다음 단계로)**

```
1. 재료 보내기 — 의도 이해
   첨부: seed-v2.md + ui-spec.md + sitemap.md + user-flow.md 원본 (요약본 만들지 않는다 — 원본이 이미 평문)
   프롬프트 틀: 서비스 한 줄 소개 + "첨부 문서로 서비스를 이해해달라.
     이 단계에서는 아무것도 제작하지 말고, 이해한 내용을 요약해서 확인시켜주고
     이해 안 되는 점을 질문해달라."
   확정 기준: 디자인 도구의 이해 요약이 기획과 일치 — 특히 서비스 용어와 1층 메뉴
   (어긋난 부분은 여기서 교정)

2. 레퍼런스 보내기 — 톤 정렬
   첨부: 톤 레퍼런스 화면 ~5장 (로컬 보유분에서 선별)
   프롬프트 틀: "우리가 닮고 싶은 분위기의 화면들이다. 공통된 인상을 언어로 정리해
     확인시켜달라. 아직 제작하지 않는다."
   확정 기준: 정리된 톤 언어가 우리 분위기 선언과 일치
   (레퍼런스 미보유 시: 이 단계를 "준비 후 진행"으로 표시하고 3단계로 건너뛸 수 있음을 명시)

3. 와이어프레임 다듬기 — 구조 (대화하며 진행)
   첨부: wireframe.html (우리가 만든 색 없는 와이어프레임 — 공통 섹션, 페이지별 화면, 상태 화면, 와이어플로)
   프롬프트 틀: "첨부한 와이어프레임은 1단계 사이트맵의 페이지·섹션 번호(P4, P4-3)로 라벨을 붙인
     저해상도 구조다. 섹션 구성과 순서, 번호 라벨은 그대로 두고, 실제 화면 비율과 요소 모양으로
     다듬어달라. 아직 색과 장식은 쓰지 않는다. {첫 묶음 페이지 목록 — wireframe.md 첫 묶음}부터.
     섹션을 더하거나 빼거나 순서를 바꾸는 편이 낫다고 보면 바로 바꾸지 말고 번호로 제안해달라."
   확정 기준: 모든 화면이 섹션 번호와 하나씩 대응 + 상태 화면 포함 + 기획자 승인. 조정은 대화로.
   구조가 바뀌는 제안을 받아들였으면 가이드에 "기획 문서 반영 필요"로 적는다
     (sitemap.md 갱신 또는 discovery-sitemap 다시 만들기 — 디자인 도구 쪽에서만 바꾸고 끝내지 않는다).

4. 색·디자인 테마 — 스켈레톤에 입히기 (대화하며 진행)
   프롬프트 틀: "확정된 스켈레톤에 색과 스타일을 입혀달라. 방향: {분위기 선언 전문}.
     {하지 말 것}. 2~3안을 보여달라 → 선택 후 확정된 팔레트·타이포를 정리해달라."
   확정 기준: 팔레트·타이포 정리본 확정 (이것이 5단계의 입력)

5. Tailwind 테마 + 공통 컴포넌트 — 코드로
   프롬프트 틀: "확정 테마를 Next.js + Tailwind 프로젝트용으로 넘겨달라:
     ① Tailwind 테마 파일(색 토큰·폰트) ② 공통 컴포넌트 {후보 목록 — sitemap.md 공통 섹션 +
     와이어프레임에서 여러 페이지에 반복되는 요소}을
     테마를 적용한 컴포넌트 코드로."
   확정 기준: 테마 파일이 FE 프로젝트에 그대로 들어갈 형태 + 컴포넌트가 후보 목록 커버

6. 페이지별 스크린샷 — 최종 시안
   프롬프트 틀: "확정된 테마와 컴포넌트로 전 페이지의 최종 시안을 페이지별 이미지로 내보내달라.
     파일 이름은 페이지 번호로 시작해달라 (P4-모임-페이지.png, 상태 화면은 P4-비로그인.png).
     {전체 페이지 목록 — sitemap.md 페이지 목록} {상태 화면 목록 — user-flow.md 화면 상태 목록}."
   확정 기준: 전 페이지 + 상태 화면 수령 → FE 구현 트랙으로 인계
```

## Output

```
{입력 문서가 있는 run 디렉토리}/
  design_handoff/
    request-guide.md   ← 6단계 가이드 (프롬프트는 복붙 가능한 완성문) + 정해야 할 값
    handoff.json
```

handoff.json: 입력 경로들, 레퍼런스 보유 여부, 정합성 검사 여부, 정해야 할 값 개수,
next_step: "디자인 도구에서 1단계부터 진행 (외부)"
