# design-request-guide — 실행 예시

> 이 예시는 사이트맵·유저 흐름·와이어프레임 단계가 생기기 전 버전으로 실행한 기록이다.
> 지금 버전은 `Run:` 하나로 같은 run의 기획 문서 다섯 개를 읽고, 3단계에서 wireframe.html을 첨부해
> "새로 만들기"가 아니라 "다듬기"를 요청한다. 아래의 `Value:`·`Spec:` 인자와 3단계 문구는 이전 버전의 것이다.

실행 대상: 크루 매거진 커뮤니티 앱 (원본: `try_project_discovery_2/planner/260918-1754-crew-magazine-community-app/design_handoff/`, 2026-09-20 — 첫 생성 `efefe40`, 레퍼런스 반영 `23e0742`, 전송 패키지 `954804c`)

## 호출

```
/dk-discovery-bundle:design-request-guide Value: value-proposal/seed-v2.md Spec: ui-spec/ui-spec.md Refs: design_handoff/references/
```

원래 스킬 이름은 `cc_design_handoff:v1-request-guide`이다. `Refs:`는 넣지 않아도 된다. 넣지 않으면 2단계를 "레퍼런스 준비 후 진행"으로 표시한 가이드가 나온다.

## Input

- `value-proposal/seed-v2.md`: 서비스를 한 줄로 소개하는 문장의 재료다. 1단계에 원본 그대로 첨부된다.
- `ui-spec/ui-spec.md`: 전역 분위기 문단, 페이지 10개 목록, 페이지별 상세를 제공한다. 3·4·6단계 프롬프트에 이 내용이 채워지고, 1단계에 원본 그대로 첨부된다.
- `design_handoff/references/selection.md`: 전송 5곳과 각 곳에서 봐달라고 할 점을 제공한다. 2단계 프롬프트가 이 표로 만들어진다.

## Output

```
design_handoff/
  request-guide.md  ← 106줄. 6단계 각각에 첨부 / 복붙 프롬프트 / 확정 기준
  handoff.json      ← stages: 6, references_ready: true, references_selected 5곳
```

실제 전송용으로는 `design_package/` 폴더에 request-guide.md, seed-v2.md, ui-spec.md, references/(전송 5곳 캡처와 selection.md, reference-notes.md)를 모아 두었다(커밋 `954804c`, `23e0742`).

### 6단계 개요

| 단계 | 하는 일 | 첨부 |
|------|--------|------|
| 1 | 재료 보내기 — 서비스를 이해했는지 확인만 하고 아무것도 만들지 않는다 | seed-v2.md + ui-spec.md 원본 |
| 2 | 레퍼런스 보내기 — 분위기를 말로 정리하게 한다 | 전송 5곳 캡처 |
| 3 | 스켈레톤 UI — 색과 장식 없이 구조만 잡는다 | 없음 |
| 4 | 색·디자인 테마 — 스켈레톤에 입히고 2~3안 중 고른다 | 없음 |
| 5 | Tailwind 테마 파일 + 공통 컴포넌트 코드 | 없음 |
| 6 | 페이지별 최종 시안 이미지 | 없음 |

한 번에 다 보내지 않고 한 단계씩 보낸다. 구조(3단계)를 색(4단계)보다 먼저 확정해서, 구조를 정할 때 스타일 취향이 끼어들지 않게 한다.

### 한 단계 전체 (2단계 — 레퍼런스 보내기)

> ## 2단계 — 레퍼런스 보내기 (톤 정렬)
>
> **첨부:** `design_handoff/references/` 중 선별 5곳의 캡처
> (오늘의집 · Medium · 29CM · Meetup · 쿠팡 — 상세는 references/selection.md)
>
> **복붙 프롬프트:**
>
> > 레퍼런스 화면들을 첨부합니다. 전부 닮으라는 것이 아니라, 화면마다 봐줄 지점이 다릅니다:
> >
> > - **오늘의집**: 콘텐츠(집들이 글)가 발견으로 이어지는 구조와 피드의 톤 — 우리 서비스와 같은 뼈대
> > - **Medium**: 아티클 읽기 화면의 여백과 타이포그래피 — 우리 매거진 뷰어가 지향하는 기준
> > - **29CM**: 상품을 "읽을거리처럼" 다루는 카드와 편집 톤
> > - **Meetup**: 모임 도메인의 표준 정보 구조 (그룹·이벤트 화면 구성) — 톤이 아니라 구조 참조
> > - **쿠팡**: **사용성만** 봐주세요 — 빠른 탐색, 명확한 정보 위계, 효율적인 리스트.
> >   시각적 톤은 따르지 않습니다.
> >
> > 이 재료들을 바탕으로, 우리 서비스가 가질 분위기를 당신의 언어로 정리해서 확인시켜주세요.
> > 아직 제작은 하지 않습니다.
>
> **확정 기준:** 정리된 톤이 우리 선언("동네 독립잡지 — 사진과 글이 주인공, UI는 조용한
> 배경")과 일치하고, 쿠팡이 톤 레퍼런스가 아니라는 점을 맞게 이해.

### 한 단계 전체 (3단계 — 스켈레톤 UI)

> **첨부:** 없음 (1단계에서 보낸 ui-spec.md 기준)
>
> **복붙 프롬프트:**
>
> > 이제 제작을 시작합니다. 먼저 **색과 장식이 전혀 없는 와이어프레임(스켈레톤)**을
> > 페이지별로 만들어주세요. 앞서 보낸 UI 기획 문서의 "페이지별 상세" 섹션이 기준입니다.
> > 화면마다 구성 요소와 위치만 잡아주세요 — 스타일 판단은 다음 단계에서 합니다.
> >
> > 이 5개 화면부터 순서대로: ① 홈(매거진·참석 기록 피드, 상단 참석 확인 카드)
> > ② 모임 페이지(아카이브가 기본 탭인 4탭 구조) ③ 매거진 뷰어(하단에 모임 카드와
> > 좋아요·스크랩) ④ 모임 찾기(카드에 최근 활동 기록 미리보기 포함) ⑤ 참석 기록 작성
> > (이벤트 자동 첨부, 1분 안에 끝나는 가벼움).
> > 하단 탭은 3개입니다: 홈 · 모임 찾기 · MY.
>
> **확정 기준:** 각 화면의 배치가 UI 기획과 일치 + 내 승인. 어긋나면 이 단계에서 대화로
> 조정 (색 얘기는 아직 꺼내지 않는다).

프롬프트에 `{페이지 목록}` 같은 빈칸이 남아 있지 않다. 화면 이름과 각 화면의 핵심 구성은 ui-spec.md의 페이지별 상세에서 그대로 가져왔다.

### 4·5단계에서 기획 문서가 들어간 부분

4단계 프롬프트에는 ui-spec.md의 전역 분위기 문단 전체와 "하지 말 것" 목록이 들어간다.

> 하지 말 것: 상품 진열형 카드 그리드, 구형 리스트 UI, 첫 화면을 차지하는 프로모션 배너.

5단계에서 요청하는 공통 컴포넌트 7종은 UI 기획에서 뽑은 것이다.

> 매거진 카드(피드용) · 모임 카드(최근 활동 기록 미리보기 포함) · 이벤트 카드(날짜·장소·참여 버튼) · 참석 확인 카드 · 하단 탭바 · 가입 조건/심사 뱃지 · 좋아요·스크랩 버튼.

## 참고

- 유저가 대화에 참여하지 않고 자동으로 도는 단계다. 기획 문서에 없는 내용은 프롬프트에 넣지 않는다.
- 레퍼런스가 없을 때 먼저 돌려도 된다. 이 run에서도 처음 생성할 때(`efefe40`)는 레퍼런스가 없어서 2단계에 "※ 레퍼런스 준비 후 진행" 표시와 일반적인 문구만 들어 있었다. 레퍼런스 5곳을 고른 뒤(`23e0742`) 2단계가 위의 사이트별 문구로 바뀌었고, handoff.json의 `references_ready`도 false에서 true로 바뀌었다.
- 1단계에 보낼 요약 문서를 따로 만드는 스킬(v1-intent-brief)이 원래 있었지만 삭제됐다(`3e3557b`). 기획 산출물이 이미 평문이라 원본 파일을 그대로 첨부하면 된다는 유저 결정이었다.
