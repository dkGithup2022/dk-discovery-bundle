# Consistency Fix Workflow v1 — /dk-discovery-bundle:discovery-consistency-fix

> **이 동작은 에이전틱(agentic)한 동작입니다.**
> 아래의 명령을 수행하되, 한 번의 수정으로 끝내지 마세요.
> "완성 조건" 체크리스트로 스스로 점검하고, 미달 항목이 있으면 해당 단계로 돌아가 다시 수행하세요.
> 이 스킬은 **유저가 "고친다"로 정한 문제만** 고칩니다. 새로 판단하지 않습니다.
> 고치다가 유저 판단이 새로 필요한 곳이 나오면, 스스로 정하지 말고 다음 회차 검사로 넘기세요.

## 목적

discovery-consistency-check가 찾고 유저가 처리를 정한 문제 중 "고친다"인 것을 앞 단계 문서에 반영한다.
수정이 끝나면 다음 회차 검사가 수정 결과를 다시 본다 (최대 3회차).

이 스킬이 스스로 판단하지 않는 이유: 판단이 필요한 것은 검사 단계에서 유저가 이미 정했다.
수정 단계가 새 판단을 섞으면, 유저가 모르는 결정이 문서에 들어가고 다음 검사도 그것을 기준 삼게 된다.

## 참조 레퍼런스

```
You MUST read these before starting:
  consistency-check-items.md — 문제의 종류와 판단 기준
  sitemap-guide.md, user-flow-guide.md, wireframe-guide.md — 고칠 문서의 형식과 번호 규칙
  tools/wireframe-gen/README.md — 와이어프레임을 고칠 때 그림 데이터의 모양과 생성기 실행법
  tone-guide.md — 산출물 언어 규칙
  git/git-verification.md — 커밋 규칙
```

## 입력

```
필수:
  consistency/round-{N}/findings.md — 처리가 확정된 문제 목록 (진행 상태: 처리 확정)
  고칠 대상 문서: seed-v2.md, ui-spec.md, sitemap.md, user-flow.md, wireframe.md, wireframe.html
  와이어프레임 두 파일은 손으로 고치지 않는다 — wireframe/.gen/ 아래 그림 데이터를 고치고 생성기로 다시 만든다:
    wireframe.html ← gen.py가 .gen/dsl.py 등에서 만든다
    wireframe.md   ← mdgen.py가 만든다. 결정 기록은 .gen/decisions.json, 추가 후보는 .gen/candidates.json을 고친다
findings.md가 "유저 확인 전"이면 시작하지 않는다 — 검사 단계의 처리 결정을 먼저 받으라고 안내한다.
```

## 진행 순서

### 0. 준비

```
consistency/handoff.json에서 회차 N을 읽는다.
findings.md에서 처리가 "고친다"인 문제만 뽑는다.
  findings.md 처리 칸과 handoff.json 건수가 다르면 findings.md를 따른다
  (유저가 보류를 "고친다"로 바꾼 뒤 handoff.json이 그대로인 경우가 있다). 수정 뒤 handoff.json을 맞춘다.
와이어프레임을 고치는 문제가 있으면 먼저 생성기를 확인한다:
  wireframe/.gen/이 있는지, run 사본(scratchpad)에서 다시 만든 결과가 커밋본과 같은지.
  .gen/이 없거나 결과가 다르면 고치지 않고 멈춘다 — 손으로 고친 흔적이 있다는 뜻이라 유저에게 알린다.
round-{N}/fix-log.md가 이미 있으면 이어서 한다 (완료된 문제는 건너뛴다). 이어서 할 때:
  - fix-log.md에 "## 이어서 — {무엇 때문에}" 절을 덧붙인다. 앞 절은 고치지 않는다
  - handoff.json의 fixed·passed_to_next_round는 누적으로 쓰고, 이번 실행분은 "resumed" 필드에 따로 적는다
  - 커밋 메시지는 "{N}회차 이어서"로 구분한다
  - 새로 반영하는 결정이 이미 고친 문제의 결과를 없애면, 되돌리지 않고 fix-log에
    "R{N}-xx의 {무엇}이 R{N}-yy 반영으로 없어짐"을 적는다
```

### 1. 수정 순서 정하기

```
앞 단계 문서부터 고친다: seed-v2 → ui-spec → sitemap → user-flow → wireframe
  뒤 문서는 앞 문서의 번호와 이름을 참조하므로, 앞을 먼저 고쳐야 뒤를 한 번에 맞출 수 있다.
한 문제가 여러 문서에 걸치면 문서 순서대로 나눠 고친다.
```

### 2. 문서별 수정

```
문제마다 findings.md의 수정 제안 중 유저가 고른 것을 그대로 적용한다.
  - 처리 칸이 위치를 지정했으면 그 위치와, 그 위치를 참조하는 뒤 문서만 고친다
  - 제안이 넣을 글자를 직접 적었는데 기존 문서 표현과 조금 다르면, 뜻이 같은 한 기존 표현을 따르고 fix-log에 적는다
  - 제안이 바꾸라고 한 원문이 문서에 없으면, 같은 뜻의 문장을 그 자리에 덧붙이고 fix-log와 결정 기록에
    "바꿀 원문이 없었다"고 적는다. 덧붙이면 뜻이 달라지면 고치지 않고 넘긴다
  - 제안 안에서 다시 갈래가 나뉘어 하나를 골라야 하면, 제안 글자만으로 그릴 수 있는 쪽을 고르고
    "고쳤지만 확인할 점"에 고른 것과 이유를 적는다
번호 규칙 (모든 문서 공통):
  - 한 번 붙인 페이지·섹션·흐름·기능 번호는 바꾸지 않는다
  - 섹션을 중간에 넣어야 하면 앞 섹션 번호에 소문자를 붙인다 (P11-3 뒤 → P11-3a). 뒤 번호를 밀지 않는다
  - 섹션 안에 요소(버튼, 안내 글)를 더하는 것은 번호를 만들지 않는다. "담는 내용"만 고친다
  - 지운 것은 취소선으로 남긴다. 번호를 재사용하지 않는다. 번호 없는 문장(정책 문장, 설명 문장)도
    유저 결정으로 지울 때는 취소선으로 남기고 새 문장을 이어 적는다
수정한 문서의 결정 기록에 한 줄 추가한다. 칸 수는 그 문서 결정 기록 표에 맞춘다:
  seed-v2 부록 (# · 무엇을 · 어떻게 결정 · 유저 답변 원문) → | {다음 #} | {무엇을} | 정합성 검사 R{N}-{순번} 처리 반영 | {처리 원문} |
  ui-spec (대화 · 유저가 바꾼 것)                        → | consistency {N}회차 | {무엇을} — 검사 R{N}-{순번}: "{처리 원문}" |
  sitemap · user-flow (단계 · 무엇을 · 유저 답변 원문)     → | consistency {N}회차 | {무엇을} | 검사 R{N}-{순번}: "{처리 원문}" |
  wireframe → .gen/decisions.json에 같은 세 칸으로 넣고 mdgen.py로 다시 만든다
결정 기록의 옛 줄은 고쳐 쓰지 않는다. 원래 무엇을 정했는지가 사라지기 때문이다.
  옛 줄 끝에 "→ consistency {N}회차(검사 R{N}-{순번})에서 바꿈: {무엇으로}"를 덧붙이고 새 줄도 넣는다.
  대리 확인 줄을 유저 결정으로 확정할 때도 같은 방법으로 덧붙인다.
진행 상태·확정 표시는 건드리지 않는다 (이 수정은 이미 유저가 정한 것을 반영하는 것이다).
```

### 3. 참조 따라가기

```
고친 곳을 가리키는 뒤 문서의 참조를 찾아 함께 맞춘다.
  예: sitemap.md에서 섹션 이름을 바꿨으면 user-flow.md 노드 글자와 wireframe.html 박스 이름도 바꾼다
참조를 맞추는 것은 새 판단이 아니다. 단, 맞추려면 새 판단이 필요하면(예: 이름을 바꿨더니 흐름의 분기가
의미를 잃음) 고치지 않고 fix-log.md의 "다음 회차로 넘김"에 적는다.
  판별: 결정 문구가 적용 범위를 한정하지 않았으면, 같은 요소가 있는 모든 자리에 적용하는 것은 참조 맞추기다.
  새 화면 요소나 새 경로를 더해야 하면 새 판단이다 (검사 워크플로 3단계와 같은 문장)
무엇을 참조로 보는가:
  - 맞춘다: 번호·이름을 가리키는 곳, 고친 뒤 틀린 말이 되는 설명 문장(경위를 한 줄 덧붙인다), handoff.json의 개수
  - 두다: 결정 기록과 점검 기록 안의 옛 글자 — 당시 기록이다. 필요하면 경위 한 줄만 덧붙인다
  - 화면 상태의 뜻을 바꾸면: user-flow.md 화면 상태 목록의 "언제 생기는가"·"나온 흐름", 그 상태를 가리키는
    흐름 노드, .gen/의 상태 화면 데이터를 함께 고친다
wireframe.html은 그림 데이터에서 바뀐 섹션만 고치고 생성기로 다시 만든다 (손으로 HTML을 고치지 않는다).
  다시 만든 뒤 git diff로 바뀐 곳이 고친 섹션·박스·와이어플로뿐인지 확인한다. 다른 곳이 바뀌었으면 원인을 찾는다.
  생성기는 sitemap.md와 user-flow.md도 읽는다. 두 문서를 고쳤으면 와이어프레임을 고치는 문제가 없어도 다시 만든다.
```

### 4. 기록

```
fix-log.md에 문제마다: 문제 번호, 고친 문서·위치, 바꾸기 전 원문, 바꾼 뒤 원문, 따라 고친 참조.
한 문제를 일부만 고쳤으면 고친 부분은 "고친 것"에, 못 고친 부분은 "다음 회차로 넘김"에 나눠 적고 건수는 "부분"으로 센다.
고쳤지만 유저가 확인해야 할 점(제안 안에서 하나를 고름, 결정 문구에 없는 순서를 정해야 했음)은
"고쳤지만 확인할 점"에 적는다. 다음 회차 검사가 이 표를 먼저 읽는다.
```

### 5. 점검

```
"완성 조건"으로 점검한다. 미달이면 2~4단계로 돌아간다.
기계로 확인할 수 있는 것(번호 참조가 모두 존재하는가, mermaid 파싱, HTML id 중복, 생성기 재생성 대조)은
스크립트로 확인한다. mermaid 파싱 방법은 검사 워크플로 2단계와 같다 (Node + jsdom + mermaid 11).
와이어프레임에 요소를 더한 페이지는 브라우저로 핵심 행동 버튼(강조 버튼)이 첫 화면 경계 위에 있는지 잰다.
```

### 6. 산출과 다음 단계

```
fix-log.md와 consistency/handoff.json을 갱신하고 커밋한다.
다음 단계:
  N < 3 → discovery-consistency-check ({N+1}회차)
  N = 3 → 마지막 회차 규칙을 지키고, 검사 워크플로의 "루프 마무리"를 이 스킬이 한다. 그 뒤 design-request-guide로 넘어간다.

마지막 회차 규칙 (N = 3, 이 수정 뒤에는 검사가 없다):
  - "다음 회차로 넘김"을 남기지 않는다. 고칠 수 없는 것은 summary.md "루프 뒤 유저 확인 목록"에 올린다
  - "고쳤지만 확인할 점"도 같은 목록에 올린다
  - 고친 쪽만 점검하지 않는다. 검사 스킬이 매 회차 돌리는 기계 점검을 모두 돌리고 fix-log "점검"에 적는다:
      번호 참조, 이동 표 양쪽(C1, 세지 않는 이동 제외), 화면 상태 표 줄 수, 흐름 구조(나가는 선이 없는 노드,
      답 라벨이 둘 미만인 분기), 와이어플로 노드·선 라벨 수, mermaid 파싱, id 중복, 생성기 재생성 대조
```

## 완성 조건

```
□ 처리가 "고친다"인 문제가 모두 fix-log.md에 있다 (고침 / 부분 / 다음 회차로 넘김 중 하나)
□ "의도한 것"·"보류" 문제는 하나도 고치지 않았다
□ 바꾼 곳마다 바꾸기 전 원문과 바꾼 뒤 원문이 있다
□ 기존 번호가 바뀐 곳이 없다 (새 번호는 소문자 덧붙임만, 지운 것은 취소선)
□ 고친 곳을 가리키는 뒤 문서의 참조가 모두 맞춰졌다 (스크립트로 확인)
□ 수정한 문서마다 결정 기록에 consistency 줄이 있고, 칸 수가 그 문서 표와 같다
□ 결정 기록의 옛 줄을 지우거나 고쳐 쓴 곳이 없다 (덧붙이기만)
□ wireframe.html·wireframe.md는 생성기로 다시 만들었고, diff가 고친 곳만 바뀌었다
□ 요소를 더한 페이지의 핵심 행동 버튼이 첫 화면 경계 위에 있다 (잰 값을 fix-log "점검"에 적었다)
□ mermaid가 파싱되고, wireframe.html의 id가 겹치지 않는다
□ 새 판단이 필요한 곳을 스스로 정하지 않고 "다음 회차로 넘김"에 적었다
□ N = 3: "다음 회차로 넘김"이 0이고, 기계 점검을 모두 돌렸고, summary.md가 있다
□ 내부 용어·발명 조어 노출 0 (tone-guide)
미달 시: 해당 단계로 돌아가 보완한다. 보완 불가하면 "최소 기준 미달: {항목} — {사유}"를 fix-log.md 상단에 적는다.
```

## Output

```
discovery/{run-id}/
  consistency/
    round-{N}/fix-log.md
    handoff.json (갱신)
    summary.md          ← N = 3일 때 (검사 워크플로 "루프 마무리")
  (그리고 고친 앞 단계 문서들)
```

### fix-log.md 구조

```markdown
# 정합성 수정 {N}회차

기준: round-{N}/findings.md (처리 확정)

## 고친 것
| 문제 | 문서·위치 | 바꾸기 전 | 바꾼 뒤 | 따라 고친 참조 |

## 다음 회차로 넘김
| 문제 | 왜 고치지 못했나 | 필요한 판단 |

## 고쳤지만 확인할 점
| 문제 | 무엇을 골랐나 | 왜 | 다른 선택지 |

## 점검
| 무엇을 | 방법 (스크립트 / 브라우저) | 결과 |
```

### handoff.json (갱신 필드)

검사 스킬이 쓴 필드(findings, to_fix, deferred …)는 지우지 않고 남기고, 아래 필드만 덮어쓴다 (병합).
to_fix·deferred가 findings.md와 다르면 findings.md에 맞춰 고치고, 남은 questions_for_user는 지운다.

```json
{
  "tool": "dk-discovery-bundle:discovery-consistency-fix",
  "round": 1,
  "fixed": 8,
  "partially_fixed": 0,
  "passed_to_next_round": 1,
  "checks_for_next_round": 0,
  "touched_docs": ["ui-spec/ui-spec.md", "sitemap/sitemap.md", "user-flow/user-flow.md", "wireframe/wireframe.html"],
  "next_step": "dk-discovery-bundle:discovery-consistency-check"
}
```

## Commit

```
git add consistency/ 와 이번에 고친 문서만 → staged 검증 (git/git-verification.md)
git commit -m "discovery(consistency-fix): {N}회차 — 고침 {a}건·넘김 {b}건 ({고친 문서 나열})"
```
