# User Flow Workflow v1 — /dk-discovery-bundle:discovery-user-flow

> **이 동작은 에이전틱(agentic)한 동작이며, 두 지점에서 유저 확인을 받습니다.**
> 아래의 명령을 수행하되, 한 번의 생성으로 끝내지 마세요.
> "완성 조건" 체크리스트를 기준으로 스스로 점검하고,
> 미달 항목이 있으면 해당 단계로 돌아가 다시 수행하는 식으로,
> **완성될 때까지 반복적으로 LLM 호출(생성→점검→수정)을 이어가 답을 도출하세요.**
> 단, "유저 확인" 표시가 있는 두 지점(2. 흐름 목록 확정, 9. 전체 확인)에서는 유저의 결정을 대신 내리지 마세요.
> 사이트맵에 없는 화면이나 이동이 나와도 사이트맵을 스스로 고치지 말고, 추가 후보로 모아 9단계에서 유저에게 물으세요.

확정된 사이트맵을 받아 **유저 흐름**을 만든다: 고객군마다 핵심 과업을 골라, 과업 하나를 하는 동안
어떤 화면을 어떤 순서로 거치고, 어디서 갈라지고, 실패하면 어디로 가는지를 흐름 하나에 그림 하나로 그린다.
흐름의 화면은 사이트맵의 페이지 번호로 가리킨다. 흐름을 그리다 사이트맵에 없는 화면이나 이동 표에 없는 이동이
나오면 추가 후보로 모아 유저에게 확인받고, 사이트맵 단계로 돌아가 반영한다.
산출물은 다음 단계인 와이어프레임의 입력이 된다 — 와이어프레임은 흐름에서 나온 화면 상태 목록
(비로그인, 빈 목록, 오류, 불러오는 중 등)을 보고 페이지마다 기본 모양 외에 어떤 상태를 더 그릴지 정한다.

## 진행 순서

### 0. 재료 읽기와 전제 확인

```
- 입력 문서를 모두 읽는다.
- 사이트맵의 진행 상태가 "전체 확정"인지 확인한다. 아니면 discovery-sitemap의 전체 확인을 먼저 마치도록 안내하고 멈춘다.
- 서비스 용어는 사이트맵의 "서비스 용어" 표를 그대로 쓴다. 흐름의 노드 글자와 시작·목표 문장에 쓰인다.
- seed-v2에서 고객군을 모두 뽑고, 고객군마다 서비스에 와서 끝내려는 일(핵심 과업)을 한 줄씩 적어 둔다.
  이 목록이 1단계의 재료다.
- 이미 user-flow.md가 있으면 진행 상태를 읽고, 이어서 할지 처음부터 할지 유저에게 묻는다.
  `Resume:` 인자를 주고 불렀으면 묻지 않고 그 단계부터 이어간다 (SKILL.md "Argument Parsing").
```

### 1. 그릴 흐름 목록 정하기

```
두 종류의 흐름을 모은다.
  핵심 과업 흐름 — 고객군마다 핵심 가치에 닿는 과업. 0단계에서 적은 과업마다 흐름 하나를 후보로 둔다.
    핵심 기능 번호마다 그 기능을 쓰는 흐름이 있는지 본다. 어느 흐름에도 나오지 않는 핵심 기능이 있으면
    그 기능을 쓰는 과업이 빠진 것이므로 흐름 후보를 더하거나, 빠진 이유를 목록 옆에 적는다.
  흔한 흐름 — 로그인·가입, 온보딩, 검색처럼 여러 서비스에 공통으로 있는 흐름.
    ui-spec 보조 기능에 해당 기능이 있을 때만 넣는다.
    user-flow-guide.md의 "기본 흐름 틀"에서 가져와 이 서비스의 페이지 번호와 용어에 맞게 조정만 한다.
흐름마다 적는다: 번호(F1…), 이름, 누가, 시작 한 줄, 목표 한 줄, 다루는 기능 번호,
  가져온 틀(기본 흐름 틀에서 가져왔으면 틀 이름, 새로 그렸으면 "없음").
  "누가" 칸에는 seed-v2의 고객군 이름을 쓴다. 과업에서 맡는 역할이 따로 있으면 괄호로 덧붙이고
  (예: 모임 운영자(심사자)), 모든 고객군이 하는 흐름은 "모든 고객군"이라고 적는다.
시작과 목표를 한 줄씩 쓸 수 없는 흐름은 과업이 두 개 이상 섞인 것이므로 나눈다.
두 사람이 번갈아 참여하는 과업(예: 가입 신청 → 운영자 심사)은 사람마다 흐름을 따로 만들지 않고
흐름 하나로 두되, 목록에 참여하는 사람을 모두 적는다.
경쟁사 자료가 있으면 같은 과업을 경쟁사가 몇 걸음으로 처리하는지 참고로 붙인다 (출처: shots.md 파일명).
```

### 2. 흐름 목록 확정 — 유저 확인 1

```
1단계의 흐름 목록을 표로 보여주고 묻는다: 빠진 과업이 있는가, 빼도 되는 흐름이 있는가,
  시작과 목표가 맞는가.
  - 핵심 기능 중 어느 흐름에도 들어가지 않은 것이 있으면 함께 보여준다
  - 판단이 갈리는 흐름(예: 흔한 흐름을 이 서비스에서 따로 그릴 가치가 있는가)은 이유와 함께 묻는다
유저가 확정하기 전에 3단계로 넘어가지 않는다.
  흐름 목록이 바뀌면 그 흐름에 들인 3~7단계 작업을 다시 해야 하기 때문이다.
유저 결정 원문은 결정 기록에 보존한다.
확정되면 user-flow.md에 흐름 목록과 결정 기록을 쓰고, 진행 상태를 "흐름 목록 확정"으로 적은 뒤 중간 커밋한다 ("Commit").
  중단된 뒤 다시 부를 때 이 진행 상태를 보고 3단계부터 이어간다.
대화형이 아닌 환경이면 이 확인을 건너뛰고 1단계 목록 그대로 3단계로 간다 (SKILL.md 전제 조건 1).
  진행 상태는 "유저 확인 전 초안"으로 적는다.
```

### 3. 흐름마다 성공 경로 그리기

```
흐름마다 시작점(원)에서 출발해 목표(원)까지 아무 문제 없이 가는 길을 먼저 그린다.
  - 화면 노드에는 사이트맵 페이지 번호를 붙인다 (P4 모임 페이지, M1 가입 신청서)
  - 특정 섹션에서 일어나는 행동이면 유저 입력 노드 글자 끝에 섹션 번호를 쓴다 (가입 신청을 누른다 P4-3)
  - 화면 노드의 이름은 sitemap.md의 페이지 이름을 그대로 쓰고, 상태를 가리킬 때만 " · 상태"를 덧붙인다
    (user-flow-guide.md "번호 규칙")
  - 화면과 화면 사이에 유저가 하는 행동을 유저 입력(평행사변형)으로 넣는다
  - 사이트맵에 맞는 화면이 없으면 "(추가 후보) 이름"으로 그리고 멈추지 않고 계속 그린다.
    추가 후보는 6단계에서 모아 한 번에 다룬다
흔한 흐름은 기본 흐름 틀을 옮겨 온 뒤, 틀의 화면을 이 서비스의 페이지 번호로 바꾸고
이 서비스에 없는 단계는 지운다.
도형과 mermaid 문법은 user-flow-guide.md의 "구성 요소"와 "표현 형식"을 따른다.
노드 글자에 괄호가 들어가면 글자를 따옴표로 감싼다 (A4[/"카테고리를 고른다 P3-2 (선택)"/]).
```

### 4. 분기와 실패 경로 채우기

```
성공 경로를 한 걸음씩 따라가며 벗어나는 경우를 더한다.
  - 유저 입력마다: 틀리게 입력하거나, 비워 두거나, 올린 파일이 조건에 맞지 않는 경우가 있는가.
    있으면 실패 결과(알약)와 되돌아갈 자리(재시도) 또는 실패로 끝나는 목표(원)를 그린다
  - 로그인이 필요한 행동마다: 비로그인이면 어디로 가고, 로그인 뒤 어디로 돌아오는가
  - 목록과 검색 결과마다: 항목이 하나도 없으면 무엇을 보여주는가
  - 분기(마름모)마다: 나가는 선 양쪽이 모두 어딘가에 도착하는가
  - 횟수 제한, 파일 크기, 글자 수 같은 조건은 주석으로 붙인다.
    조건 값이 입력 문서에 없으면 지어내지 않고 "조건 미정"으로 적어 9단계에서 묻는다
```

### 5. 두 사람이 주고받는 흐름 나누기

```
1단계에서 두 사람 이상이 참여한다고 적은 흐름을 사람마다 칸(subgraph)으로 나눈다.
  - 사람마다 자기 칸 안에 시작과 목표를 둔다
  - 한 사람의 행동이 다른 사람에게 넘어가는 지점(알림, 링크, 메시지)을 칸 사이의 선으로 잇고,
    선에 무엇으로 넘어가는지 적는다
  - 넘겨받은 사람이 반응하지 않는 경우(심사하지 않음, 링크를 열지 않음)도 분기로 그릴지 본다
```

### 6. 사이트맵·이동 표와 대조

```
흐름마다 모든 화면 노드와 화면 사이의 이동을 사이트맵과 맞춰 본다.
  모달 닫기, 1층 메뉴끼리 오가기, 뒤로 가기는 대조하지 않는다. 알림이나 링크로 들어오는 이동은 대조한다
  (user-flow-guide.md "이동 표와 대조할 때 따로 대조하지 않는 이동").
  - 흐름에 나왔는데 사이트맵 페이지 목록에 없는 화면 → 화면 추가 후보
  - 흐름에 쓴 이동(A 화면에서 B 화면으로 가는 선)이 이동 표에 없는 경우 → 이동 추가 후보
  - 흐름에서 어떤 행동이 필요한데 그 행동을 담을 섹션이 해당 페이지에 없는 경우 → 섹션 추가 후보
후보마다 적는다: 구분(화면 / 이동 / 섹션), 내용, 나온 흐름 번호, 반영 방법 제안.
반대 방향으로도 본다: 이동 표에 있는데 어느 흐름에도 쓰이지 않은 이동을 모아
  "어느 흐름에도 쓰이지 않은 이동" 줄에 적는다 (사이트맵 가이드 "이동 표"가 유저 흐름 단계에 맡긴 확인이다).
  위의 대조하지 않는 이동 세 가지는 여기서도 뺀다.
  흐름은 핵심 과업과 흔한 흐름만 그리므로 쓰이지 않은 이동이 있는 것 자체는 미달이 아니다.
  그 이동이 흐름 목록에서 빠진 과업을 가리키는 것 같으면(예: 어느 흐름도 P9 내 모임 목록에 들어가지 않는다)
  9단계에서 흐름 추가를 제안한다. 이동을 지우자는 제안은 하지 않는다 — 이동 표는 사이트맵 단계가 정한 것이다.
반영 방법은 둘 중 하나를 제안한다:
  sitemap.md 갱신 — 이동 표에 줄 추가, 섹션 추가, 모달이나 트리 밖 페이지 추가, 기존 1층 페이지 아래 상세 페이지 추가처럼
    1층과 기존 페이지의 부모 관계를 건드리지 않는 변경
  discovery-sitemap 재실행 — 1층(상단 메뉴, 앱이면 하단 탭)이 바뀌거나 기존 페이지의 부모가 바뀌는 변경
이 단계에서는 sitemap.md를 고치지 않는다. 반영은 9단계에서 유저가 결정한 뒤에 한다.
```

### 7. 화면 상태 목록 뽑기

```
흐름의 분기와 실패 경로에서 나온 화면 상태를 모두 모은다
  (비로그인, 빈 목록, 결과 없음, 오류, 불러오는 중, 대기 중 — user-flow-guide.md "화면 상태").
상태 이름은 이 여섯 가지 중 하나를 쓰고, 구체적인 내용은 "언제 생기는가"에 적는다
  (P4 대기 중 — 가입 신청 뒤 운영자 심사를 기다릴 때).
상태마다 적는다: 페이지 번호와 상태 이름(P4 비로그인), 언제 생기는가, 나온 흐름 번호(와 노드).
같은 페이지의 같은 상태가 여러 흐름에서 나오면 한 줄로 합치고 흐름 번호를 모두 적는다.
이 목록은 와이어프레임 단계가 페이지마다 기본 모양 외에 어떤 상태를 더 그릴지 정하는 입력이다.
```

### 8. 점검

```
"완성 조건" 체크리스트로 점검한다. [확인 후] 표시 항목은 이 첫 점검에서 건너뛴다.
미달 항목이 있으면 아래 단계로 돌아가 고친 뒤 체크리스트 전체를 다시 점검한다.
  "흐름 목록과 기능 커버리지" 묶음 미달 → 1단계 (흐름 이름·시작·목표 글자 보완, 빠진 기능 번호나 이유 적기)
  "흐름 구조" 묶음 미달 → 3단계(목표에 닿지 않는 경로, 도형), 4단계(끝이 비어 있는 분기, 실패 경로,

  "앞 단계와의 번호 일치" 묶음 미달 → 흐름 번호·기능 번호·고객군 이름은 1단계, 페이지·섹션 번호는 3단계,
    handoff.json 개수는 산출물을 다시 쓴다
  "과정과 언어" 묶음 미달 → 해당 글자가 나온 단계
미달이 없어질 때까지, 또는 남은 미달이 모두 보완 불가로 판정될 때까지 고치기와 점검을 반복한다.
보완 불가한 항목은 "완성 조건"의 미달 시 규칙대로 경고로 남기고 9단계에서 유저에게 보여준다.
흐름을 더하거나 빼거나 나누는 것처럼 흐름 목록(2단계에서 유저가 확정한 것) 자체를 바꿔야 하는 문제는
스스로 바꾸지 않고, 9단계에서 유저에게 제안한다.
```

### 9. 전체 확인 — 유저 확인 2

```
흐름 목록, 흐름별 그림, 화면 상태 목록, 사이트맵 추가 후보를 한 번에 보여준다.
  - 아티팩트(웹 페이지) 발행이 가능한 환경이면 웹 페이지로 보여주고 (mermaid 그림이 그려진 채로),
    불가하면 user-flow.md를 그대로 보여준다
  - 사이트맵 추가 후보는 하나씩 반영할지 묻는다. 반영 방법 제안(sitemap.md 갱신 / discovery-sitemap 재실행)도 함께 확인받는다
  - 4단계에서 "조건 미정"으로 남긴 조건과 8단계에서 유저 판단이 필요한 것으로 남긴 항목도 함께 묻는다
  - 6단계에서 빠진 과업을 가리킨다고 본 "어느 흐름에도 쓰이지 않은 이동"이 있으면 흐름 추가를 제안한다.
    유저가 흐름을 더하기로 하면 흐름 목록에 새 번호로 넣고, 그 흐름만 3~8단계를 거친다
유저의 수정을 반영하고, 반영 후 8단계 점검을 다시 통과시킨다.

추가 후보의 반영:
  유저가 반영하기로 한 후보가 없으면 → 바로 확정으로 간다.
  sitemap.md 갱신으로 정한 후보만 있으면 →
    sitemap.md의 트리 그림·페이지 목록·섹션 목록·이동 표에 추가하고, 새 페이지·모달에는 사이트맵 번호 규칙대로
    다음 번호를 붙인다. sitemap.md의 진행 상태는 "전체 확정" 그대로 둔다. sitemap.md 결정 기록에 "유저 흐름 단계에서 추가"와 유저 답변 원문을 남긴다.
    sitemap/handoff.json의 개수도 맞춰 고친다.
    흐름의 "(추가 후보) 이름"을 새 번호로 바꾸고 6단계 대조와 8단계 점검을 다시 한다.
  discovery-sitemap 재실행으로 정한 후보가 하나라도 있으면 →
    user-flow.md에 진행 상태 "사이트맵 재실행 대기"와 반영할 후보 목록을 남기고 멈춘다.
    유저에게 discovery-sitemap 재실행을 안내하고, 사이트맵이 다시 확정되면
    이 스킬을 `Resume: 6`으로 불러 6단계부터 다시 하게 한다.
  유저가 반영하지 않기로 한 후보는 → 흐름에서 그 화면이나 이동을 사이트맵에 있는 화면·이동으로 바꾸거나 뺀다.
    어떻게 바꿀지 판단이 갈리면 유저에게 묻는다.
유저가 확정하면 [확인 후] 항목을 포함해 "완성 조건" 전체를 다시 점검하고, 통과하면(또는 남은 미달을 경고로 기록하면)
산출물을 쓰고 커밋한다.
```

## 완성 조건

각 항목은 user-flow.md(와 handoff.json)를 보고 참인지 거짓인지 판정한다.
[확인 후] 표시가 붙은 항목은 9단계에서 유저가 결정해야 참이 될 수 있다. 8단계 첫 점검에서는 건너뛰고,
9단계에서 유저 결정을 반영한 뒤 다시 점검할 때 판정한다.

```
흐름 목록과 기능 커버리지:
  □ seed-v2의 고객군마다 핵심 과업 흐름이 하나 이상 있다
    (흐름이 없는 고객군이 있으면 흐름 목록 아래에 그 이유가 적혀 있다)
  □ 모든 핵심 기능이 어느 흐름의 "다루는 기능"에 들어가 있다.
    들어가지 않은 핵심 기능은 "어느 흐름에도 들어가지 않은 핵심 기능" 줄에 이유와 함께 적혀 있다
  □ 흔한 흐름(로그인·가입, 온보딩, 검색 등)은 ui-spec 보조 기능에 해당 기능이 있는 것만 들어 있고,
    "가져온 틀" 칸에 기본 흐름 틀 이름이 적혀 있다
  □ 흐름 목록의 모든 줄에 번호, 이름, 누가, 시작 한 줄, 목표 한 줄, 다루는 기능, 가져온 틀이 있다
  □ 흐름 목록의 흐름과 "흐름별 그림"의 흐름이 하나씩 짝이 맞다 (목록에만 있거나 그림만 있는 흐름 0)

흐름 구조 (흐름 그림마다):
  □ 시작 원이 하나다. 두 사람이 주고받는 흐름은 사람 칸마다 하나다
  □ 시작에서 성공 목표 원까지 이어지는 경로가 있다 (목표에 도달하지 못하는 흐름 0)
  □ 분기(마름모)마다 나가는 선이 둘 이상이고, 선마다 답 라벨이 있으며, 모두 어떤 노드에 도착한다
    (끝이 비어 있는 분기 0)
  □ 목표 원과 주석이 아닌 노드는 모두 나가는 선이 하나 이상 있다
    (빠져나갈 수 없는 화면 0 — 다음 걸음, 뒤로 가기, 닫기 중 하나가 선으로 그려져 있다)
  □ 실패 경로("실패" 라벨이 붙은 선)가 하나 이상 있다. 없는 흐름은 그림 아래에 실패할 경우가 없는 이유가 적혀 있다
  □ 재시도는 기존 입력 노드로 되돌아가는 선으로 그려져 있다 (재시도하려고 같은 입력 노드를 복사한 곳 0)
  □ 도형이 user-flow-guide.md "구성 요소"와 "표현 형식"을 따른다. 괄호가 든 노드 글자는 따옴표로 감싸져 있다
    (원은 시작·목표에만 쓰고, 시스템 결과는 모두 알약이다)
  □ 서버 내부 처리를 그린 노드가 없다
  □ 두 사람이 참여한다고 목록에 적은 흐름은 사람마다 subgraph로 나뉘어 있고,
    칸 사이의 선마다 무엇으로 넘어가는지(알림, 링크, 메시지) 라벨이 있다

이동과 화면 상태:
  □ 흐름에 쓰인 화면 사이의 이동은 모두 사이트맵 이동 표에 있거나, 사이트맵 대조 결과에 이동 추가 후보로 올라 있다
    (모달 닫기, 1층 메뉴끼리 오가기, 뒤로 가기는 제외 — user-flow-guide.md "이동 표와 대조할 때 따로 대조하지 않는 이동")
  □ 흐름의 화면 노드는 모두 사이트맵 번호를 달고 있거나, "(추가 후보) 이름"으로 적혀 사이트맵 대조 결과에 올라 있다
  □ "어느 흐름에도 쓰이지 않은 이동" 줄이 있다 (없으면 "없음")
  □ [확인 후] 사이트맵 대조 결과의 모든 후보에 유저 결정과 반영 결과가 채워져 있다
  □ [확인 후] 진행 상태가 "전체 확정"이면 흐름에 "(추가 후보)" 노드와 이동 표에 없는 이동이 남아 있지 않다
    (반영한 후보는 새 번호로 바뀌어 있고, 반영하지 않기로 한 후보는 흐름에서 기존 화면·이동으로 바꾸거나 빠져 있다)
  □ 흐름의 비로그인 분기, 항목 없음·결과 없음 분기, 실패 결과, 다른 사람을 기다리는 화면에서 생기는 화면 상태가
    모두 화면 상태 목록에 있다
  □ 화면 상태 목록의 모든 줄에 페이지 번호, 상태, 언제 생기는가, 나온 흐름이 있고,
    상태 이름이 user-flow-guide.md "화면 상태"의 여섯 가지 중 하나이며,
    같은 페이지의 같은 상태가 두 줄 이상 있지 않다
  □ 흐름마다 적은 "이 흐름에서 나온 화면 상태"와 화면 상태 목록의 "나온 흐름"이 서로 맞다

앞 단계와의 번호 일치:
  □ 화면 노드의 페이지 번호(P·M·X)와 유저 입력 노드의 섹션 번호(P4-3)가 모두 sitemap.md에 있다
  □ 화면 노드의 이름이 sitemap.md의 페이지 이름과 같다 (이름 뒤에 덧붙인 " · 상태"는 빼고 비교한다)
  □ 기능 번호가 ui-spec의 번호와 일치한다 (새로 매긴 기능 번호 0)
  □ "누가" 칸이 seed-v2의 고객군 이름으로 적혀 있다 (괄호 안 역할과 "모든 고객군"은 허용)
  □ 흐름 번호가 겹치지 않는다. 삭제한 흐름은 취소선으로 남아 있고 그 번호를 다른 흐름이 쓰지 않는다
  □ sitemap.md를 갱신했으면, 새 페이지·모달 번호가 사이트맵 번호 규칙대로 이어지고,
    sitemap.md 결정 기록에 "유저 흐름 단계에서 추가"와 유저 답변 원문이 있으며, sitemap/handoff.json의 개수가 sitemap.md와 맞다
  □ handoff.json의 flows 목록과 screen_states 개수, sitemap_candidates 개수가 user-flow.md와 맞다

과정과 언어:
  □ [확인 후] 유저 확인 두 번(흐름 목록 확정, 전체 확인)을 거쳤고, 결정 원문이 결정 기록에 있다
  □ 주석의 조건 값(용량, 횟수, 글자 수)은 입력 문서에 근거가 있거나 "조건 미정"으로 적혀 있다
    (study 레퍼런스 이미지의 값 20MB, 3~5회 등을 근거 없이 옮긴 곳 0)
  □ [확인 후] "조건 미정"으로 남은 조건마다 유저에게 물은 기록이 결정 기록에 있다
  □ 흐름 이름, 노드 글자, 시작·목표 문장이 사이트맵의 서비스 용어와 일치한다
  □ 경쟁사 자료를 참고한 곳에 출처(shots.md 파일명)가 있다
  □ 내부 용어·발명 조어 노출 0 (tone-guide 산출물 언어 규칙)

미달 시: 8단계 점검에 적힌 단계로 돌아가 보완한다. 보완 불가하면
"최소 기준 미달: {항목} — {사유}" 경고를 user-flow.md 상단(진행 상태 줄 아래)에 기록한다 (강제로 채우지 않는다).
예: 실패 경로를 만들 근거가 입력 문서에 없는데 실패 경로를 지어내지 않는다. 경고로 남기고 9단계에서 유저에게 묻는다.
대화형이 아닌 환경의 초안에서는 유저 확인·유저 결정에 관한 항목([확인 후] 표시 항목)을 판정하지 않고
"유저 확인 전"으로 남긴다. 이 항목들은 최소 기준 미달 경고로 적지 않는다.
```
