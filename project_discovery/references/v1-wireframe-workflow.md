# Wireframe Workflow v1 — /dk-discovery-bundle:discovery-wireframe

> **이 동작은 에이전틱(agentic)한 동작이며, 두 지점에서 유저 확인을 받습니다.**
> 아래의 명령을 수행하되, 한 번의 생성으로 끝내지 마세요.
> "완성 조건" 체크리스트를 기준으로 스스로 점검하고,
> 미달 항목이 있으면 해당 단계로 돌아가 다시 수행하는 식으로,
> **완성될 때까지 반복적으로 LLM 호출(생성→점검→수정)을 이어가 답을 도출하세요.**
> 단, "유저 확인" 표시가 있는 두 지점(4. 공통 섹션과 첫 묶음 확인, 10. 전체 확인)에서는 유저의 결정을 대신 내리지 마세요.
> 사이트맵에 없는 섹션·요소나 유저 흐름에 없는 화면 상태가 필요해도 sitemap.md와 user-flow.md를 스스로 고치지 말고,
> 추가 후보로 모아 10단계에서 유저에게 물으세요.

확정된 사이트맵과 유저 흐름을 받아 **와이어프레임**을 만든다: 사이트맵의 페이지별 섹션 목록을 위에서 아래로
박스로 쌓고 섹션 번호와 이름을 라벨로 붙여, 페이지 안에서 무엇이 어디에 놓이는지를 색과 장식 없이 그린다.
유저 흐름에서 나온 화면 상태(비로그인, 빈 목록, 오류 등)마다 기본 모양에서 바뀌는 섹션을 따로 그리고,
유저 흐름 하나마다 화면 프레임을 순서대로 화살표로 이어 와이어플로를 만든다.
화면과 섹션은 사이트맵의 번호(P4, P4-3)로, 흐름은 유저 흐름의 번호(F1)로 가리킨다.
산출물은 외부 파일 없이 브라우저로 바로 열리는 HTML 한 장이다. 이 파일은 클로드 디자인 3단계에 첨부 파일로 넘어가,
3단계 요청을 "와이어프레임을 만들어달라"에서 "이 와이어프레임을 다듬어달라"로 바꾼다.
다음 단계는 design-references이고, design-references를 이미 마쳤으면 design-request-guide다.

## 진행 순서

"유저 확인" 표시가 있는 단계는 4단계와 10단계 두 곳이다.
나머지 단계는 에이전트가 스스로 그리고 점검하며, 유저에게 묻지 않는다.

### 0. 재료 읽기와 전제 확인

```
- 입력 문서를 모두 읽는다.
- sitemap.md와 user-flow.md의 진행 상태가 모두 "전체 확정"인지 확인한다.
  아니면 해당 스킬(discovery-sitemap / discovery-user-flow)의 전체 확인을 먼저 마치도록 안내하고 멈춘다.
- user-flow.md의 흐름 그림에 "(추가 후보)" 노드가 남아 있으면 멈춘다.
  사이트맵에 번호가 없는 화면은 프레임을 그릴 수 없기 때문이다. discovery-user-flow를 다시 부르도록 안내한다.
- 사이트맵이 유저 흐름 확정 뒤에 바뀌었는지 확인한다 (프로젝트 루트에서 실행):
    git log -1 --format=%cI -- discovery/{run-id}/sitemap/sitemap.md
    git log -1 --format=%cI -- discovery/{run-id}/user-flow/user-flow.md
  둘 중 하나라도 커밋 기록이 없으면 이 확인을 건너뛰고, 건너뛴 사실을 결정 기록에 적는다.
  sitemap.md의 마지막 커밋이 이 스킬 10단계의 "discovery(sitemap): 와이어프레임에서 나온 추가 반영" 커밋이면
  넘어간다. 이 커밋은 기존 섹션 번호를 바꾸지 않으므로 유저 흐름과 다시 대조할 필요가 없다.
  그 밖의 커밋으로 sitemap.md의 마지막 커밋이 더 나중이면, 유저 흐름이 지금 사이트맵과 대조되지 않았을 수 있다.
  유저에게 알리고 discovery-user-flow를 `Resume: 6`으로 불러 대조를 다시 하도록 안내한다.
  유저가 그대로 진행하기로 하면 결정 기록에 남기고 진행한다. 대화형이 아닌 환경이면 멈춘다.
- 플랫폼을 sitemap.md 머리줄에서 읽어 프레임 폭을 정한다 (앱 360px, 웹 640px, 둘 다면 두 폭).
  둘 다이면 페이지별 기본 모양은 두 폭으로 그리고(열 배치가 같으면 앱 폭 하나와 "웹도 같은 배치"),
  상태 화면과 와이어플로는 앱 폭 하나로만 그린다. 상태 화면은 바뀐 섹션을 보이는 것이 목적이라 폭을 두 번 그릴 필요가 없다.
- 서비스 용어는 sitemap.md의 "서비스 용어" 표를 그대로 쓴다. 프레임 제목, 요소 이름, 버튼 이름에 쓰인다.
- 경쟁사 자료가 있으면, 사이트맵 페이지마다 같은 성격의 경쟁사 캡처가 있는지 짝을 지어 메모해 둔다
  (예: P4 모임 페이지 ↔ 경쟁사 A의 모임 상세 캡처). 3·5단계에서 섹션 크기를 정할 때 본다.
- git 상태를 확인한다 (git/git-verification.md "Dirty 체크 스코프 규칙").
- 이미 wireframe/wireframe.md가 있으면 진행 상태를 읽고, 이어서 할지 처음부터 할지 유저에게 묻는다.
  `Resume:` 인자를 주고 불렀으면 묻지 않고 그 단계부터 이어간다 (SKILL.md "Argument Parsing").
  대화형이 아닌 환경이면 묻지 않고, 기존 파일을 건드리지 않은 채 멈춘다 (SKILL.md 전제 조건 3).
```

### 1. 그릴 목록과 첫 묶음 정하기

```
무엇을 몇 장 그릴지를 먼저 목록으로 만든다. 이 목록이 9단계 점검에서 빠진 그림을 찾는 기준이 된다.
  페이지 프레임 — sitemap.md 페이지 목록의 모든 페이지 (탭·상세·모달·트리 밖).
    취소선으로 삭제된 페이지는 뺀다. 템플릿 페이지는 프레임 하나로 센다.
    페이지마다 섹션 수를 적어 둔다 (박스 수와 맞춰 볼 숫자다).
  상태 화면 — user-flow.md "화면 상태 목록"의 모든 줄. 한 줄에 상태 화면 하나다.
  와이어플로 — user-flow.md "흐름 목록"의 모든 흐름. 취소선으로 삭제된 흐름은 뺀다.
이 문서에서 "핵심 과업 흐름"은 user-flow.md 흐름 목록의 "다루는 기능" 칸에 핵심 기능 번호
  (s가 붙지 않은 번호)가 하나 이상 있는 흐름을 말한다. 보조 기능(s1…)만 다루는 흐름(로그인·가입 등)은 아니다.
  "가져온 틀" 칸으로 가리지 않는다. 핵심 과업도 기본 흐름 틀을 가져올 수 있기 때문이다 (user-flow-guide.md 예시의 F2).
첫 묶음을 정한다. 첫 묶음은 4단계에서 유저가 먼저 보고 그리는 방식을 확정하는 페이지들이다.
  - 핵심 과업 흐름 중 번호가 가장 앞선 흐름 하나를 고른다
  - 그 흐름의 성공 경로(user-flow-guide.md "흐름을 이루는 경로")에 나오는 페이지를 첫 묶음으로 한다.
    두 사람이 주고받는 흐름이면 흐름 목록 "누가" 칸에 먼저 적힌 사람의 칸만 본다.
    선 라벨에 다른 흐름 번호가 붙은 화면(F4를 거치는 X1)은 그 흐름의 화면이므로 넣지 않는다.
    다섯 개를 넘으면 흐름 순서대로 앞 다섯 개만 넣는다
  - 핵심 과업 흐름이 없으면 1층 탭 페이지를 첫 묶음으로 한다
  - 어느 흐름을 왜 골랐는지 한 줄로 적는다
    (예: F1 모임 가입 신청과 심사 — 핵심 기능 11, 12를 다루는 흐름 중 번호가 가장 앞서서.
    신청자 칸의 성공 경로에서 P4, M1)
  첫 묶음을 핵심 과업의 페이지로 잡는 이유: 유저가 가장 신경 쓰는 화면에서 그리는 방식을 확정해야,
  나머지 페이지를 같은 방식으로 그린 뒤에 다시 그리는 일이 줄어든다.
이 목록을 wireframe.md "그린 범위"에 미리 채워 둔다. 그림을 그릴 때마다 해당 줄에 표시한다.
```

### 2. 공통 섹션 그리기

```
sitemap.md "공통 섹션" 표의 섹션을 하나씩, 한 번만 그린다 (wireframe-guide.md "구성 요소"의 공통 섹션).
  - 섹션 안의 요소는 공통 섹션 표의 "담는 내용"에 적힌 것만 그린다
  - 표의 "쓰이는 페이지"를 섹션 아래 동작 주석으로 적는다
  - 페이지에 따라 요소가 조금 다르면(예: 1층 탭 화면에는 뒤로가기가 없다) 모양을 두 벌 그리지 않고
    동작 주석으로 적는다
이때 HTML 파일의 틀(머리, <style>, 목차)도 함께 만든다. 모양과 규칙은 wireframe-guide.md "표현 형식"을 따른다.
```

### 3. 첫 묶음 페이지의 기본 모양 그리기

```
첫 묶음의 페이지마다 프레임을 하나 그린다. 모든 규칙은 wireframe-guide.md "모양", "번호 규칙",
"그릴 때 지키는 규칙"을 따른다.
  - 프레임 제목에 페이지 번호, 이름, 유형을 적는다. 유형은 sitemap.md 섹션 목록 제목처럼 괄호 안에 쓴다
    (P4 모임 페이지 (상세, 템플릿)). " · "는 상태 화면 제목에만 쓰므로 유형 앞에 쓰지 않는다
  - 섹션 목록의 순서대로 섹션 박스를 위에서 아래로 쌓고, 박스마다 섹션 번호와 이름, 담는 기능 번호를 라벨로 붙인다
  - 공통 섹션은 2단계에서 그린 모양을 그대로 가져온다
  - 섹션 안에는 "담는 내용"에 적힌 요소만, wireframe-guide.md "요소 자리 모양" 표의 모양으로 그린다
  - 섹션끼리의 상대 크기는 담는 내용의 양으로 정한다. 경쟁사 캡처가 있으면 같은 성격 섹션의 크기를 참고하고
    그 섹션에 출처(shots.md 파일명)를 적는다
  - 화면에서 가장 중요한 버튼 하나만 진한 회색으로 채운다. 이 문서에서 "핵심 행동 버튼"은 이 버튼을 말한다.
    어느 버튼인지는 이 페이지가 나오는 핵심 과업 흐름(1단계의 정의)에서
    다음 화면으로 넘어가는 행동으로 정한다. 그런 흐름이 여럿이면 번호가 가장 앞선 흐름을 따른다.
    그 행동이 버튼 누르기가 아니면(쓰기, 고르기) 그 섹션의 "담는 내용"에서 행동을 마치는 버튼(제출, 저장)을 채우고,
    그런 버튼이 없으면 채우지 않는다. 이 페이지가 어느 핵심 과업 흐름에도 나오지 않으면 채우지 않는다
  - 첫 화면 경계를 가로 점선으로 긋는다. 핵심 행동 버튼이 이 선 아래에 있으면
    4단계에서 유저에게 보여주고 물을 항목으로 적어 둔다
그리다가 섹션 목록에 없는 섹션이나 담는 내용에 없는 요소가 필요해 보이면 그리지 않는다.
  추가 후보로 적어 두고 계속 그린다. 추가 후보는 8단계에서 모아 한 번에 다룬다.
유저에게 보이기 전에, "완성 조건"의 "공통 섹션" 묶음과 "페이지 프레임" 묶음을 첫 묶음 페이지에 대해 먼저 점검하고
미달을 고친다. 다른 묶음은 나머지를 다 그린 뒤 9단계에서 점검한다.
```

### 4. 공통 섹션과 첫 묶음 확인 — 유저 확인 1

```
2·3단계의 그림을 보여준다.
  - 보여주기 전에 wireframe.html을 공통 섹션과 첫 묶음까지 파일로 써 둔다 (커밋은 하지 않는다).
    머리의 진행 상태 칸에는 "유저 확인 전 초안"을 적고, 확정되면 "첫 묶음 확정"으로 바꾼다
  - 아티팩트(웹 페이지) 발행이 가능한 환경이면 wireframe.html을 웹 페이지로 보여주고,
    불가하면 wireframe.html의 파일 경로를 알려 브라우저로 열어 보게 한다
묻는 것:
  - 요소 자리를 그리는 방식과 박스 안의 밀도가 알아보기 쉬운가. 나머지 페이지도 이 방식으로 그린다는 점을 함께 말한다
  - 공통 섹션의 모양이 맞는가
  - 섹션끼리의 상대 크기가 맞는가. 핵심 행동 버튼이 첫 화면 경계 아래에 있으면 그대로 둘지 묻는다
    (그대로 두면 이유를 결정 기록에 남긴다. 섹션 순서를 바꾸자는 답이면 추가 후보로 옮긴다)
  - 3단계에서 나온 추가 후보가 있으면 함께 보여준다. 반영 여부는 10단계에서 한 번에 받는다고 알린다.
    사이트맵 수정을 한 번에 모아야 사이트맵을 여러 번 고치지 않기 때문이다
유저가 확정하기 전에 5단계로 넘어가지 않는다.
  그리는 방식이 바뀌면 나머지 페이지 전체와 상태 화면, 와이어플로를 다시 그려야 하기 때문이다.
유저의 수정을 반영하고, 반영한 뒤 첫 묶음 점검을 다시 한다. 유저 결정 원문은 결정 기록에 보존한다.
확정되면 유저 수정을 반영한 wireframe.html(공통 섹션과 첫 묶음까지)과 wireframe.md를 쓰고,
  진행 상태를 "첫 묶음 확정"으로 적은 뒤 중간 커밋한다 ("Commit").
  중단된 뒤 다시 부를 때 이 진행 상태를 보고 5단계부터 이어간다.
대화형이 아닌 환경이면 이 확인을 건너뛰고 5단계로 간다 (SKILL.md 전제 조건 1).
  진행 상태는 "유저 확인 전 초안"으로 적는다.
```

### 5. 나머지 페이지의 기본 모양 그리기

```
그릴 목록의 나머지 페이지를 4단계에서 확정한 방식으로 그린다. 규칙은 3단계와 같다.
  순서: 1층 탭 페이지 → 그 아래 상세 페이지(트리 순서) → 모달 → 트리 밖 페이지
  - 모달은 모달 자체의 섹션만 그린다. 어느 페이지의 어떤 행동이 이 모달을 부르는지는
    sitemap.md 이동 표에 적힌 대로 프레임 제목 아래 동작 주석으로 적는다
  - 첫 화면 경계 아래에 핵심 행동 버튼이 있는 페이지는 10단계에서 물을 항목으로 적어 둔다
  - 섹션 목록에 없는 섹션이나 요소가 필요해 보이면 3단계와 같이 그리지 않고 추가 후보로 적는다
10단계 뒤 사이트맵이 바뀌어 `Resume: 5`로 다시 불렸으면, sitemap.md에서 바뀐 페이지만 다시 그리고
  그 페이지의 상태 화면(6단계)과 그 페이지가 나오는 와이어플로(7단계)도 다시 그린다.
  바뀐 페이지는 wireframe.md에 남긴 "반영할 후보 목록"과, "사이트맵 재실행 대기" 커밋 이후
  sitemap.md와 user-flow.md의 git diff로 찾는다. 섹션 번호가 바뀐 페이지는 기존 박스를 고치지 않고 프레임을 새로 그린다.
```

### 6. 상태 화면 그리기

```
그릴 목록의 상태 화면을 하나씩 그린다 (wireframe-guide.md "화면 상태").
  - 같은 페이지의 기본 모양 프레임 바로 옆에 둔다. 제목은 "P4 모임 페이지 · 비로그인"처럼 적는다
  - 어느 섹션이 바뀌는지는 화면 상태 목록의 "언제 생기는가"와, user-flow.md에서 그 상태 바로 뒤에
    이어지는 선(다음 행동)을 보고 정한다
    (예: P4 비로그인 → F1에서 아니오 선이 X1 로그인·가입으로 간다 → P4-3 행동 버튼이 바뀐다)
  - 바뀐 섹션만 점선 테두리로 요소 자리를 채우고, 나머지는 "(기본 모양과 같음)"으로 둔다
  - 바뀐 섹션에 동작 주석을 붙인다: 무엇을 누르면 어디로 가는가 (사이트맵 번호, 거치는 흐름 번호)
  - 불러오는 중 상태는 요소 자리를 회색 막대로만 채운다
  - 진한 회색으로 채우는 버튼은 바뀐 섹션 안에서 이 상태를 벗어나는 행동(동작 주석에 적은 행동)의 버튼 하나다
    (P4 비로그인의 "로그인하고 가입 신청"). 누를 것이 없는 상태는 채우지 않는다
  - 어느 섹션이 바뀌는지 입력 문서만으로 판단이 갈리면 지어내지 않는다.
    가장 가능성 높은 안으로 그리고, 결정 기록에 "확인 필요"로 남겨 10단계에서 묻는다
화면 상태 목록에 없는 상태를 더 그려야 할 것 같으면(예: 목록 페이지인데 불러오는 중 상태가 목록에 없다)
  그리지 않고 상태 추가 후보로 적는다.
```

### 7. 와이어플로 그리기

```
그릴 목록의 흐름마다 와이어플로를 하나 그린다 (wireframe-guide.md "와이어플로").
user-flow.md의 그 흐름 그림(mermaid)을 노드 하나씩 옮긴다. 노드 종류마다 옮기는 모양은 이렇다
(노드 종류는 user-flow-guide.md "구성 요소"와 "표현 형식"의 도형으로 구분한다).
  - 시작·목표 원 ((…)) → 원. 글자를 그대로 적는다
  - 화면 노드 (페이지 번호가 붙은 […]) → 화면 프레임. 3·5단계 프레임을 줄여서 싣되, 섹션 박스와 라벨만 남기고
    화살표가 출발하는 섹션만 요소 자리를 그린다
  - 화면 노드 이름 뒤에 " · "가 붙어 있으면 기본 모양 대신 6단계의 상태 화면을 놓는다.
    흐름 그림의 글자(예: P4 모임 페이지 · 심사 대기)는 여섯 가지 상태 이름과 다를 수 있다.
    같은 페이지 번호이면서 "나온 흐름" 칸이 이 흐름(과 노드)을 가리키는 화면 상태 목록의 줄을 찾아
    그 상태 화면을 놓고, 프레임 제목은 상태 화면의 제목(P4 모임 페이지 · 대기 중)을 쓴다.
    맞는 줄이 여럿이면 " · " 뒤 글자를 각 줄의 "언제 생기는가"와 견주어 고른다. 그래도 하나로 정해지지 않거나
    맞는 줄이 없으면 지어내지 않는다. 가장 가까운 상태 화면(없으면 기본 모양)을 놓고
    결정 기록에 "확인 필요"로 남겨 10단계에서 묻는다
  - 단계 노드 (페이지 번호가 없는 […]) → 가는 테두리의 작은 박스. 글자를 그대로 적는다
  - 유저 입력 [/…/] → 화살표 위 문구. 유저 입력 노드로 들어오는 선마다 화살표 하나를 그리고,
    그 화살표가 입력 노드 다음 노드로 바로 이어지게 한다. 화살표 위에는 입력 글자를 그대로 적되
    글자 끝의 섹션 번호(P4-3)는 빼고, 그 섹션 박스에서 화살표를 출발시킨다.
    입력 글자에 섹션 번호가 없으면 sitemap.md 섹션 목록의 "담는 내용"에서 그 행동이 일어나는 섹션을 찾아 출발시킨다.
    찾을 수 없으면 프레임 아래 가장자리에서 출발시키고 결정 기록에 "확인 필요"로 남겨 10단계에서 묻는다
  - 분기 {…} → 마름모. 나가는 화살표마다 흐름 그림의 답 라벨을 그대로 적는다
  - 시스템 결과 ([…]) → 화면 상태 목록에 이 노드에서 나온 상태 화면이 있으면(예: 입력 오류 표시 → M1 오류)
    그 상태 화면 프레임으로 옮긴다. 없으면(예: 신청 완료) 가는 테두리의 작은 박스로 옮기고 글자 앞에 "결과:"를 붙인다
    (결과: 신청 완료). 박스로 두는 이유: 시스템 결과에서 다른 사람의 칸으로 가는 선(신청 완료 → 알림 → 운영자)이
    나가는 경우가 있어, 화살표가 출발할 자리가 있어야 한다
  - 외부 앱 [[…]] → 두 줄 테두리의 작은 박스. 앱 이름을 그대로 적는다
  - 주석 노드 (-.-로 붙은 회색 노드) → 메모 박스. 붙어 있던 노드 옆에 둔다.
    메모 박스는 점선 테두리와 회색 글자로 그려, 가는 테두리의 단계 박스와 구분한다.
    붙어 있던 노드가 유저 입력이면 그 입력을 옮긴 화살표 옆에 둔다
  - 다른 흐름을 거치는 노드 → 그 흐름의 첫 화면 프레임 하나만 두고 동작 주석에 흐름 번호를 적는다
  - 두 사람이 주고받는 흐름 → 사람마다 가로 띠를 나누고, 띠 사이 화살표에 무엇으로 넘어가는지
    (알림, 링크, 메시지)를 흐름 그림의 라벨 그대로 적는다
  - 선 → 화살표. 선 라벨(답, 실패, 알림, "F4 로그인 후 돌아온다"처럼 거치는 흐름 번호를 적은 라벨)은 그대로 적는다.
    유저 입력 노드에 붙은 선은 위 규칙대로 화살표 하나로 합친다
흐름 그림에 없는 이동은 그리지 않는다.
옮긴 뒤 wireframe.md 와이어플로 표에 흐름 그림의 노드 수와 옮긴 노드 수, 흐름 그림의 선 라벨 수와
  와이어플로에 옮긴 선 라벨 수를 세어 적고 맞춰 본다. 옮기지 않은 노드와 빠진 선 라벨이 0이어야 한다.
```

### 8. 사이트맵·유저 흐름과 대조

```
3·5·6·7단계에서 적어 둔 추가 후보를 한 표로 모은다. 후보의 종류는 네 가지다.
  섹션 — 섹션 목록에 없는 섹션이 필요하다
    (흐름의 행동을 담을 섹션이 없다, 그려 보니 한 섹션에 목적이 두 개다)
  요소 — 섹션의 "담는 내용"에 없는 요소가 필요하다.
    상태 화면의 바뀐 섹션에 넣은 안내와 버튼은 흐름의 분기에서 나온 것이므로 요소 후보로 올리지 않는다
  섹션 순서 — 섹션 순서를 바꾸는 편이 낫다 (예: 핵심 행동 버튼이 첫 화면 경계 아래에 있다)
  화면 상태 — 화면 상태 목록에 없는 상태를 그려야 한다
후보마다 적는다: 종류, 내용, 나온 곳(페이지 번호 또는 흐름 번호), 반영 방법 제안.
반영 방법은 셋 중 하나를 제안한다:
  sitemap.md 갱신 — 섹션의 담는 내용에 요소를 더하거나, 페이지 섹션 목록의 맨 끝에 섹션을 더하는 것처럼
    기존 섹션 번호가 바뀌지 않는 변경. 유저 흐름의 섹션 번호(P4-3)가 그대로 맞으므로 user-flow.md는 고치지 않아도 된다
  discovery-sitemap 재실행 — 섹션을 중간에 끼우거나, 순서를 바꾸거나, 나누거나 합치는 것처럼
    기존 섹션 번호가 바뀌는 변경. 섹션 번호가 바뀌면 유저 흐름의 번호도 다시 대조해야 하기 때문이다
  와이어프레임에만 추가 — 화면 상태 후보. user-flow.md는 고치지 않고, wireframe.md의 그린 범위에
    "와이어프레임 단계에서 추가"로 적는다
이 단계에서는 sitemap.md와 user-flow.md를 고치지 않는다. 반영은 10단계에서 유저가 결정한 뒤에 한다.
빠진 그림(박스가 없는 섹션, 그리지 않은 상태, 와이어플로가 없는 흐름)은 추가 후보가 아니라 미달이다.
  9단계에서 해당 단계로 돌아가 그린다.
```

## 완성 조건

각 항목은 wireframe.html과 wireframe.md(와 handoff.json)를 sitemap.md, user-flow.md와 나란히 놓고 보아
참인지 거짓인지 판정한다. 개수를 세는 항목은 세어 본 숫자를 wireframe.md "그린 범위" 표에 적어 두고 그 숫자로 판정한다.
[확인 후] 표시가 붙은 항목은 유저가 결정해야 참이 될 수 있다. 9단계 첫 점검에서는 건너뛰고,
10단계에서 유저 결정을 반영한 뒤 다시 점검할 때 판정한다.
3단계 끝의 첫 묶음 점검은 "공통 섹션" 묶음과 "페이지 프레임" 묶음을 첫 묶음 페이지에 대해서만 판정한다.

```
그릴 목록과 기능 커버리지:
  □ sitemap.md 페이지 목록의 모든 페이지(취소선으로 삭제된 페이지 제외)에 프레임이 하나씩 있다
    (프레임이 없는 페이지 0, 템플릿 페이지는 프레임 하나)
  □ user-flow.md 화면 상태 목록의 모든 줄에 상태 화면이 하나씩 있다 (그리지 않은 상태 0)
  □ user-flow.md 흐름 목록의 모든 흐름(취소선으로 삭제된 흐름 제외)에 와이어플로가 하나씩 있다
  □ sitemap.md 섹션 목록의 "담는 기능"에 나오는 기능 번호가 모두 어느 섹션 박스의 라벨에 있다
    (라벨에서 빠진 기능 번호 0)
  □ wireframe.md "그린 범위"의 모든 줄의 "그림" 칸이 "완료"다

공통 섹션:
  □ sitemap.md 공통 섹션 표의 섹션마다 "공통 섹션" 영역에 한 번씩 그려져 있다
  □ 공통 섹션마다 "쓰이는 페이지"가 동작 주석으로 적혀 있다
  □ 페이지 프레임 안의 공통 섹션이 "공통 섹션" 영역의 모양과 같다
    (요소의 종류, 순서, 모양이 같고, 페이지마다 다른 점은 동작 주석으로만 적혀 있다)

페이지 프레임 (프레임마다):
  □ 프레임 제목에 페이지 번호, 이름, 유형이 있다
  □ 섹션 박스 수가 sitemap.md 그 페이지의 섹션 수와 같다 (handoff.json box_section_mismatch = 0)
  □ 섹션 박스가 섹션 목록의 순서대로 위에서 아래로 쌓여 있다
  □ 섹션 박스마다 라벨에 섹션 번호와 이름이 있고, "담는 기능"이 있는 섹션은 기능 번호도 있다
  □ 섹션 안의 요소가 모두 그 섹션의 "담는 내용"에 적힌 것이다 (담는 내용에 없는 요소 0.
    필요해 보인 요소는 그리지 않고 추가 후보 표에 올라 있다)
  □ 요소 자리가 wireframe-guide.md "요소 자리 모양" 표의 모양으로 그려져 있다
    (이미지 자리는 X자 박스, 본문은 가로줄. 실제 문장이 적힌 곳 0)
  □ 진한 회색으로 채운 버튼이 프레임마다 하나 이하다
  □ 첫 화면 경계 점선이 있다
  □ 핵심 행동 버튼이 첫 화면 경계 아래에 있는 페이지는 결정 기록에 이유가 있거나,
    섹션 순서 추가 후보로 올라 있다
  □ 모달 프레임에는 그 모달을 부르는 페이지와 행동이 sitemap.md 이동 표 그대로 동작 주석으로 적혀 있다
  □ 페이지 프레임 위에 이동 화살표가 그어져 있지 않다

상태 화면 (상태 화면마다):
  □ 같은 페이지의 기본 모양 프레임과 같은 줄에 놓여 있다
  □ 제목이 "{페이지 번호} {페이지 이름} · {상태}"이고, 상태 이름이 user-flow.md 화면 상태 목록의 것과 같다
    (8·10단계에서 "와이어프레임에만 추가"로 더한 상태는 user-flow-guide.md "화면 상태" 표의 여섯 가지 이름 중 하나다)
  □ 진한 회색으로 채운 버튼이 하나 이하이고, 채운 버튼은 바뀐 섹션 안에 있다
  □ 바뀐 섹션이 하나 이상 있고, 바뀐 섹션은 점선 테두리로, 나머지 섹션은 박스와 라벨과 "(기본 모양과 같음)"으로 그려져 있다
  □ 바뀐 섹션마다 무엇을 누르면 어디로 가는지 동작 주석이 있고, 가는 곳이 사이트맵 번호로 적혀 있다
    (불러오는 중 상태는 누를 것이 없으므로 제외한다)
  □ 불러오는 중 상태는 요소 자리가 회색 막대로만 채워져 있다
  □ 입력 문서만으로 바뀐 섹션을 정할 수 없던 상태 화면은 결정 기록에 "확인 필요"로 남아 있다
  □ [확인 후] "확인 필요"로 남은 상태 화면마다 유저 결정이 결정 기록에 있다

와이어플로 (흐름마다):
  □ 제목에 user-flow.md의 흐름 번호와 이름이 있고, 누가, 시작, 목표가 한 줄씩 적혀 있다
  □ 흐름 그림의 노드가 모두 7단계의 모양으로 옮겨져 있다
    (wireframe.md 와이어플로 표의 "흐름 그림의 노드 수"와 "옮긴 노드 수"가 같다)
  □ 흐름 그림의 선 라벨이 모두 와이어플로 화살표에 그대로 있다
    (wireframe.md 와이어플로 표의 "흐름 그림의 선 라벨 수"와 "옮긴 선 라벨 수"가 같다)
  □ 유저 입력에서 나온 화살표는 모두 섹션 박스에서 출발한다. 프레임 가장자리에서 출발한 화살표는
    결정 기록에 "확인 필요"로 남아 있다. 화살표 위 문구가 흐름 그림의 유저 입력 글자(끝의 섹션 번호 제외)와 같다
  □ [확인 후] "확인 필요"로 남은 화살표 출발 섹션마다 유저 결정이 결정 기록에 있다
  □ 분기 마름모의 나가는 화살표마다 흐름 그림의 답 라벨이 그대로 적혀 있다
  □ 흐름 그림에서 이름 뒤에 " · "가 붙은 화면 노드 자리와, 화면 상태 목록의 "나온 흐름" 칸이 가리키는
    시스템 결과 노드 자리에 기본 모양이 아닌 그 상태 화면이 놓여 있다.
    짝을 하나로 정할 수 없던 자리는 결정 기록에 "확인 필요"로 남아 있다
  □ [확인 후] 7단계에서 "확인 필요"로 남은 상태 화면 짝마다 유저 결정이 결정 기록에 있다
  □ 흐름 그림에 없는 이동을 그린 화살표가 없다
  □ 다른 흐름을 거치는 곳은 그 흐름의 첫 화면 프레임 하나와, 흐름 번호를 적은 동작 주석으로 되어 있다
  □ 두 사람이 주고받는 흐름은 사람마다 가로 띠가 나뉘어 있고, 띠 사이 화살표마다 무엇으로 넘어가는지 라벨이 있다

앞 단계와의 번호 일치와 추가 후보:
  □ 프레임 번호와 이름, 섹션 번호와 이름이 sitemap.md의 것과 글자까지 같다 (새로 매긴 번호 0)
  □ 라벨의 기능 번호가 sitemap.md 섹션 목록의 "담는 기능"과 같다 (ui-spec 번호를 새로 매기거나 바꾼 곳 0)
  □ 와이어플로의 흐름 번호가 user-flow.md의 흐름 번호와 같다
  □ 3·5·6·7단계에서 그리지 않고 넘긴 섹션, 요소, 섹션 순서, 화면 상태가 모두 wireframe.md "추가 후보" 표에 있고,
    줄마다 종류, 내용, 나온 곳, 반영 방법이 채워져 있다
  □ wireframe.html "사이트맵 대조 결과"가 wireframe.md 추가 후보 표와 줄 수가 같다 (후보가 없으면 "없음")
  □ [확인 후] 추가 후보 표의 모든 줄에 유저 결정과 반영 결과가 채워져 있다
  □ [확인 후] 진행 상태가 "전체 확정"이면, 반영하기로 한 후보가 모두 그림에 들어가 있고
    "discovery-sitemap 재실행"으로 정한 후보가 남아 있지 않다
  □ sitemap.md를 갱신했으면, 기존 섹션 번호가 바뀌지 않았고, sitemap.md 결정 기록에
    "와이어프레임 단계에서 추가"와 유저 답변 원문이 있다
  □ handoff.json의 first_batch, pages, state_screens, wireflows, box_section_mismatch, primary_below_fold, candidates 값이
    wireframe.md와 맞다

HTML 표현 형식:
  □ 외부 파일을 불러오는 곳이 없다 (<link>, <script src>, <img src>, @import, url(http…) 0)
  □ 쓰인 색이 흰색, 검정, 회색뿐이다 (그림자, 그라데이션, 둥근 장식 0.
    와이어플로의 시작·목표 원과 아이콘 자리의 작은 원은 도형이라 장식으로 세지 않는다)
  □ 페이지별 프레임과 상태 화면의 폭이 sitemap.md 플랫폼과 맞다 (앱 360px, 웹 640px).
    둘 다이면 기본 모양은 두 폭(열 배치가 같은 페이지는 앱 폭과 "웹도 같은 배치")이고 상태 화면은 앱 폭이다.
    와이어플로 안의 줄인 프레임은 이 항목에서 제외한다
  □ 기본 모양 프레임 안의 섹션 박스마다 id가 섹션 번호다 (id="P4-3").
    상태 화면 id는 "{페이지 번호}-{상태 이름}"(공백은 하이픈, id="P9-빈-목록")이고,
    공통 섹션 영역의 박스 id는 "공통-{섹션 이름}"(id="공통-하단-탭")이다.
    플랫폼이 둘 다이면 웹 폭 프레임과 그 섹션 박스의 id 끝에 "-웹"을 붙인다 (id="P4-웹", id="P4-3-웹").
    상태 화면 안의 섹션 박스와 와이어플로 안의 프레임·섹션 박스에는 id가 없다. id가 겹치는 곳이 없다
  □ 파일 안의 순서가 머리, 공통 섹션, 페이지별 프레임, 와이어플로, 사이트맵 대조 결과다 ("Output")
  □ 머리의 진행 상태가 wireframe.md의 진행 상태와 같다. "최소 기준 미달" 경고가 있으면 머리에도 옮겨져 있다

과정과 언어:
  □ [확인 후] 유저 확인 두 번(공통 섹션과 첫 묶음 확인, 전체 확인)을 거쳤고, 결정 원문이 결정 기록에 있다
  □ 프레임 제목, 요소 이름, 버튼 이름이 sitemap.md 서비스 용어와 일치한다
  □ 경쟁사 캡처를 참고한 섹션에 출처(shots.md 파일명)가 있다
  □ study 레퍼런스 이미지의 페이지 이름, 섹션, 문구(Hero Banner, Sponsors 등)가 그림에 없다
  □ 내부 용어·발명 조어 노출 0 (tone-guide 산출물 언어 규칙)

미달 시: 9단계 점검에 적힌 단계로 돌아가 보완한다. 보완 불가하면
"최소 기준 미달: {항목} — {사유}" 경고를 wireframe.md 상단(진행 상태 줄 아래)에 기록하고
wireframe.html 머리에도 같은 문장을 옮긴다 (강제로 채우지 않는다).
예: 섹션의 "담는 내용"이 비어 있어 요소 자리를 그릴 근거가 없으면 요소를 지어내지 않는다.
  박스와 라벨만 그리고 경고와 요소 추가 후보로 남겨 10단계에서 유저에게 묻는다.
대화형이 아닌 환경의 초안에서는 [확인 후] 표시 항목을 판정하지 않고 "유저 확인 전"으로 남긴다.
이 항목들은 최소 기준 미달 경고로 적지 않는다.
```

그림은 wireframe.html 한 장에 모두 싣는다. 진행 상태와 유저 답변 원문은 wireframe.md에 따로 둔다.
클로드 디자인에 넘기는 파일에 작업 기록이 섞이면 배치가 아닌 내용까지 읽고 판단하게 되기 때문이다.
추가 후보를 sitemap.md 갱신으로 반영한 경우에만 sitemap/sitemap.md도 함께 바뀐다.

### wireframe.html 구조

wireframe-guide.md "표현 형식"의 규칙(외부 파일 없음, 흰색·검정·회색만, 섹션 박스 id=섹션 번호)을 따른다.
파일 안에 싣는 순서는 이렇다.

```html
<!doctype html>
<html lang="ko">
<head>
  <meta charset="utf-8">
  <title>와이어프레임 — {서비스 한 줄}</title>
  <style>/* 스타일 전부 여기에. 외부 파일 없음 */</style>
</head>
<body>
  <header>
    <h1>와이어프레임 — {서비스 한 줄}</h1>
    <p>기준 문서: {사이트맵 경로} · {유저 흐름 경로} · 플랫폼: 앱 | 웹 | 둘 다 · 진행 상태: {진행 상태}</p>
    <p>읽는 법: 박스 = 사이트맵 섹션, 박스 왼쪽 위 = 섹션 번호와 이름, 점선 박스 = 상태에 따라 바뀐 섹션,
       가로 점선 = 첫 화면 경계, ··· = 동작 주석</p>
    <nav><!-- 목차: 공통 섹션, 페이지별 프레임(페이지 번호 목록), 와이어플로(흐름 번호 목록) --></nav>
  </header>

  <section id="common"><h2>공통 섹션</h2>
    <!-- 공통 섹션 표의 섹션마다 한 번. 쓰이는 페이지를 동작 주석으로 -->
  </section>

  <section id="pages"><h2>페이지별 프레임</h2>
    <!-- 페이지 번호 순서(P → M → X). 한 페이지의 기본 모양과 상태 화면을 한 줄(div.row)에 나란히 -->
    <div class="row">
      <section class="frame" id="P4">…</section>             <!-- 기본 모양 -->
      <section class="frame state" id="P4-비로그인">…</section> <!-- 상태 화면 -->
    </div>
  </section>

  <section id="flows"><h2>와이어플로</h2>
    <!-- 흐름 번호 순서. 흐름마다 제목(F1 흐름 이름), 누가, 시작, 목표 한 줄씩 적고 아래에 그림.
         화살표와 마름모는 인라인 SVG -->
    <section class="flow" id="F1">…</section>
  </section>

  <section id="candidates"><h2>사이트맵 대조 결과</h2>
    <!-- wireframe.md "추가 후보" 표에서 종류, 내용, 나온 곳, 반영 결과만 옮긴다 (유저 답변 원문은 옮기지 않는다).
```

- 머리는 파일 맨 위의 `<header>` 부분이다.
- 상태 화면의 id는 "{페이지 번호}-{상태 이름}"으로 붙이고 상태 이름 안의 공백은 하이픈으로 바꾼다
  (id="P4-비로그인", id="P9-빈-목록"). 섹션 id(P4-3)와 겹치지 않는다.
- 공통 섹션 영역의 박스 id는 "공통-{섹션 이름}"이다. 섹션 이름 안의 공백도 하이픈으로 바꾼다 (id="공통-헤더", id="공통-하단-탭").
- 플랫폼이 둘 다이면 웹 폭 기본 모양 프레임과 그 안의 섹션 박스 id 끝에 "-웹"을 붙인다 (id="P4-웹", id="P4-3-웹").
  앱 폭 프레임은 규칙 그대로(id="P4", id="P4-3") 둔다.
- id는 공통 섹션 영역, 기본 모양 프레임과 그 안의 섹션 박스, 상태 화면 프레임, 와이어플로(id="F1")에만 붙인다.
  상태 화면 안의 섹션 박스와 와이어플로 안에 줄여 실은 프레임에는 id를 붙이지 않는다. 같은 id가 두 번 나오지 않게 하기 위해서다.
- 진행 상태가 "유저 확인 전 초안"이면 머리의 첫 줄에 "유저 확인 전 초안"을 크게 적는다.
- "최소 기준 미달" 경고가 있으면 머리의 진행 상태 줄 아래에 그대로 옮긴다.

### handoff.json

```json
{
  "version": "1.0",
  "tool": "dk-discovery-bundle:discovery-wireframe",
  "generated_at": "ISO timestamp",
  "input_docs": {
    "sitemap": "sitemap/sitemap.md",
    "user_flow": "user-flow/user-flow.md"
  },
  "output": "wireframe/wireframe.html",
  "platform": "app",
  "first_batch": ["P4", "M1"],
  "common_sections": ["헤더", "하단 탭"],
  "pages": 12,
  "state_screens": 7,
  "wireflows": ["F1", "F2", "F3", "F4"],
  "box_section_mismatch": 0,
  "primary_below_fold": ["P5"],
  "candidates": { "proposed": 3, "accepted": 1, "applied_by": "sitemap.md 갱신" },
  "next_step": "dk-discovery-bundle:design-references"
}
```

- `pages`는 그린 페이지 프레임 수다 (템플릿은 하나로 센다). `state_screens`는 그린 상태 화면 수다.
- `box_section_mismatch`는 섹션 목록의 섹션 수와 박스 수가 다른 페이지의 수다. 완성이면 0이다.
- `primary_below_fold`는 핵심 행동 버튼이 첫 화면 경계 아래에 남은 페이지다 (유저가 그대로 두기로 한 것).
- `applied_by`는 반영한 방법이다: "sitemap.md 갱신" / "discovery-sitemap 재실행" / "와이어프레임에만 추가".
  두 가지 이상이면 배열로 적고(재실행 대기 뒤 `Resume: 5`로 돌아와 확정한 경우 포함), 반영한 후보가 없으면 null.
- `next_step`: 현재 run에 design_handoff/references/selection.md가 있으면 design-references를 이미 마친 것이므로
  "dk-discovery-bundle:design-request-guide", 없으면 "dk-discovery-bundle:design-references".
- 대화형이 아닌 환경에서 초안만 만든 경우와 "사이트맵 재실행 대기"로 멈춘 경우에는 next_step을 비워 둔다.
