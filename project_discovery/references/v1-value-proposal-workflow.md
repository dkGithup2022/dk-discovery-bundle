# Value Proposal Workflow v1 — /dk-discovery-bundle:discovery-value-proposal

> **이 동작은 유저와의 대화가 본체인 단계입니다.**
> 조사·가설 재료를 유저가 눈으로 보게 하고, 무엇을 채택·강조·보류·제외할지 유저가 결정하게
> 하고, 그 결정을 문서로 정리하는 것이 전부입니다. 유저의 답을 대신 정하지 마세요.
> 산출물 작성 시에는 "완성 조건"을 기준으로 스스로 점검하고, 미달이면 보완하여 완성하세요.

가설 재료(hypothesize 산출물)를 유저와 함께 검토하여, 원본 seed의 상세판인
**Seed v2 (가치 관점 기획)**를 만든다. Seed v2는 다음 단계(페이지별 UI 기획, 기획서)의
기준 문서가 된다.

## 산출물 미리보기 — Seed v2가 담는 것

원본 seed의 구조(아이디어/고객/가치)를 유지하면서 각 항목을 채택된 가설로 상세화한 문서:
- 아이디어: 원문 보존 + 구체화 (+ 원본에서 바뀐 결정이 있으면 명시)
- 핵심 고객: 세그먼트로 정밀화 + 초기 공략 순서 + 각 세그먼트에서 작동하는 심리
- 제공 가치: 핵심 가치 블록(강조된 것) + 기본으로 있어야 하는 기능 + 옵션
- 채택하지 않은 것 (보류/제외 + 이유)
- 남은 확인 과제 (리스크)
- 부록: 결정 기록 표 (무엇을 / 어떻게 결정 / 유저 답변 원문)

## Step 1 — 열람 자료 제시 ("눈으로 보는" 단계)

```
유저가 결정하기 전에 재료 전체를 훑을 수 있는 열람 자료를 만들어 제시한다.

구성 (4부):
  1. 시드 — 원문 그대로
  2. 경쟁사 — 서비스별 강점(+)/약점(−) 대비, 가격·수익 모델·규모, 스크린샷 참조.
     analysis와 화면 기록이 모순됐던 항목은 정정 내용과 함께 표시
  3. 가설 — 상위/하위/기능 카드 전체. 분류와 근거 수준을 색·배지로 구분하되
     각 배지에 한 줄 정의를 함께 표시 (용어가 자료 안에서 자립하게)
  4. 쟁점·미검증 — 결정 전에 알아야 할 것만 모음. 확인 안 된 가정이 무엇인지,
     유저의 체감 판단이 왜 중요한지 안내

표현 형식:
  - 아티팩트(웹 페이지) 발행이 가능한 환경이면 웹 페이지로 만든다.
    필수 요소: ① 목차 (섹션·소제목) ② "지금 보는 중" 표시 — 유저가 스크롤할 때
    현재 위치(섹션 › 소제목 › 항목)가 항상 보이게
  - 발행이 불가한 환경이면 같은 구성의 마크다운 문서로 제시한다

유저에게 링크(또는 문서)를 주고, 다 봤다는 신호를 받은 뒤 Step 2로 간다.
```

## Step 2 — 채택 대화 (질문 라운드)

```
AskUserQuestion으로 결정을 수집한다. 기본 2라운드, 라운드당 최대 4문.

라운드 1 — 가장 결정적인 것부터:
  1~2. 확인 안 된 가정(추론 태그) 중 seed의 성립에 가장 중요한 것 1~2건의 체감 검증
       — "체감상 맞나요?" (선택지: 맞다-체감 일치 / 방향 맞음-조사 필요 / 일부만 / 회의적)
       유저가 "맞다"고 하면 그 가설은 확인된 것으로 처리하고 경위(유저 체감 확인)를 명시
  3. 차별화 카드 중 핵심 가치로 강조할 것 (복수 선택)
  4. 미검증 카드의 처리 (채택-베팅 / 일부만 / 보류-조사 후)

라운드 2 — 마무리:
  1. 라운드 1의 답이 만든 후속 질문 (예: 강조에서 빠진 차별화 카드의 위상 —
     채택 / 강조 승격 / 옵션 축소 / 보류)
  2. 기본 기능의 범위 (전부 채택 / 순서 조정 / 일부 제외)
  3. 가설에서 도출된 전략 갈림길 1건 (예: 두 고객군 중 초기 공략 대상)
  4. 자유 선언 — "추가로 강조하고 싶은 요소나 방향이 있으세요?"
     Other 선택 시 줄글 입력, 추가 기획서 파일이 있으면 경로를 받는다

질문 작성 규칙:
  - 모든 질문에 맥락을 담는다: 무엇이 걸려 있는 결정인지 한 줄로
    (예: "seed의 성장 전제가 여기 걸려 있습니다")
  - 선택지마다 그 선택이 무엇을 의미하는지 description으로 설명
  - 내부 용어 금지 — 질문 문구도 산출물 언어 규칙을 따른다
  - 유저 답변은 원문 그대로 보존한다. 해석해서 바꾸지 않는다
```

## Step 3 — Seed v2 생성

```
채택 대화의 결정을 반영해 value-proposal/seed-v2.md를 작성한다.

작성 규칙:
  - 원본 seed의 문장은 "원문 (보존):"으로 그대로 남기고, 구체화를 별도로 쓴다
  - 유저 결정이 원본 seed를 수정하는 경우 (예: 필수 기능 → 옵션 축소)
    "원본에서 바뀐 것"으로 명시하고 결정 번호를 단다
  - 모든 주장에 근거를 유지한다 (가설 번호·analysis·스크린샷 인용 — hypothesize에서 승계)
  - 확인 안 된 가정이 유저 체감으로 확인됐으면 "확인된 것으로 처리 + 확인 경위"를 쓴다.
    체감 확인은 조사를 대체하지 않으므로, 출시 후 확인할 신호는 리스크에 남긴다
  - 채택되지 않은 항목도 버리지 않는다 — "채택하지 않은 것" 표에 이유와 함께 기록
  - 결정 기록 부록: | 무엇을 | 어떻게 결정 | 유저 답변 원문 | 표
  - 언어: tone-guide 산출물 언어 규칙 전면 적용. 이 문서는 3개월 뒤의 본인과
    이 과정을 모르는 동료가 읽는다

완성 조건:
  □ 원본 seed의 모든 섹션이 상세화되어 있음 (누락 없음)
  □ 채택 대화의 모든 결정이 문서 어딘가에 반영됨 (결정 기록 표와 대조)
  □ 유저 답변 원문이 보존됨
  □ 확인 안 된 가정의 현재 상태가 전부 명시됨 (확인됨/대비책/조사 대기/출시 후 확인)
  □ 내부 용어·발명 조어 노출 0 (스스로 재독하여 확인)
미달이면 보완 후 다시 점검한다.
```

## Step 4 — 열람 자료에 결정 반영

```
Step 1의 열람 자료를 갱신한다 — 결정 전 자료가 아니라 현재 상태판이 되도록:
  - 각 카드·가설에 결정 배지 (강조 / 채택 / 옵션 축소 / 보류 / 제외)
  - 확인 안 된 가정의 현재 상태 갱신
  - 다음 단계 안내 갱신
아티팩트로 발행했다면 같은 URL로 재발행한다.
```
