# Hypothesize Workflow v1.1 — /dk-discovery-bundle:discovery-hypothesize

> **이 동작은 에이전틱(agentic)한 동작입니다.**
> 아래의 명령을 수행하되, 한 번의 생성으로 끝내지 마세요.
> "Phase 5 — 완성 조건" 체크리스트를 기준으로 스스로 점검하고,
> 미달 항목이 있으면 해당 Phase로 돌아가 다시 수행하는 식으로,
> **완성될 때까지 반복적으로 LLM 호출(생성→점검→수정)을 이어가 답을 도출하세요.**

research(경쟁 서비스 분석)와 service-recording(경쟁 서비스 화면 기록)의 산출물을 재료로,
**"사람들이 무엇을 원하고, 어떤 조건이 충족되어야 움직이며, 그래서 무엇을 만들어야 하는가"에
대한 가설 문서**를 만든다. 산출물은 이후 단계인 placement(기능/UI 배치)와
proposal(기획서 작성)의 직접 입력이 된다.

## 용어 정의 (이 문서에서 쓰는 모든 용어 — 먼저 읽을 것)

| 용어 | 정의 |
|------|------|
| **상위 기획 가설** | 서비스가 존재할 이유에 대한 수요 명제. "사람들은 어떤 종류의 모임/서비스를 원할 것이다"처럼, 무엇을·누가 원하는지에 대한 가설. seed의 고객·가치에서 도출한다. |
| **하위 기획 가설** | 기능을 정하기 전에 참이어야 하는 유저 심리·니즈 명제. "어떤 심리적 조건이 충족되어야 사람들이 실제로 행동하는가"에 대한 가설. 예: "처음 가서 뻘쭘할 것 같다는 공포가 해소되어야 참여한다", "이상한 사람이 없다는 보장이 있어야 오프라인 모임에 나온다" |
| **기능 가설 카드** | 하위 기획 가설을 충족하기 위해 무엇을 만들면 되는지에 대한 가설. 화면·기능 수준. 아래 카드 형식으로 기록한다. |
| **기본기** | 시장의 모든 경쟁 서비스가 제공하고 있어서, 없으면 유저가 서비스를 떠나는 필수 요소 (영어로 table stakes). 차별화가 아니라 "없으면 지는 것". |
| **차별화** | 경쟁 서비스가 제공하지 않아서, 우리가 제공하면 경쟁에서 이기는 근거가 되는 요소. |
| **미검증** | 유망해 보이지만 유저가 실제로 원한다는 증거가 아직 없는 요소. 조사 대상. |
| **공급측 근거** | "경쟁사가 그 기능을 만들어 놓았다"는 사실. 만들었다는 것 자체는 유저가 원한다는 증거가 아니다. |
| **수요측 근거** | "유저가 실제로 원한다/쓴다"는 증거. 지불하는 가격, 리뷰에서의 반복 언급, 실사용 규모 등. |
| **근거 쟁점** | analysis 문서의 주장과 스크린샷 기록이 서로 모순되는 항목. |
| **종류** | 하나의 가설이 세 가지 중 어디에 속하는지 — 상위 기획 가설 / 하위 기획 가설 / 기능 가설 카드. |

## 전체 구조

두 방향에서 재료를 추출한 뒤, 위의 세 종류 가설로 정리한다:

```
추출 1 (Pass 1): 경쟁사가 충족하지 못하는 것 찾기
                 — 약점, 제공하지 않는 기능, 비어 있는 가격대
추출 2 (Pass 2): 경쟁사가 잘하고 있어서 유저가 실제로 쓰는 것 찾기
                 — 당연해 보이는 것 포함. 검증된 니즈의 원천
        ↓ 정리
상위 기획 가설 (수요)  →  하위 기획 가설 (심리·니즈 조건)  →  기능 가설 카드 (수단)
```

**끝나는 조건:** 상위 기획 가설 1~3개 + 하위 기획 가설 3~7개 + 기능 가설 카드 7개 이상
(기본기 2개 이상, 차별화 3개 이상 포함), 모든 카드에 근거·분류·검증 신호·연결 가설이 있고,
추가 조사 필요 여부 판정이 완료되었을 때.

> v1.1 변경: 가설을 상위 기획/하위 기획/기능 카드 세 종류로 구분,
> 기본기 분류에 대한 수요 증거 예외 규칙 신설, Pass 2 니즈·근거 쟁점·Critic 기록 위치 지정,
> 추가 조사 판정 범위를 모든 가설로 확장, Pass: 2 모드의 기존 산출물 승계 규칙 명시.

## Phase 0 — 근거 정합성 체크 (읽기 직후, 추출 시작 전)

```
analysis 문서의 강점/약점 주장과 shots.md의 화면 기록을 대조한다.
  모순 발견 시 (예: analysis에는 "가입 전 정보가 부족하다"라고 쓰여 있는데
  실제 화면 캡처에는 멤버 수·일정·게시판이 공개되어 있는 경우):
    → 화면 기록을 우선한다. 직접 관찰한 것이 간접 수집한 것보다 신뢰도가 높다.
    → 해당 항목에 "쟁점: analysis와 화면 기록 불일치 — {내용}" 태그를 달고,
      이후 이 항목을 근거로 쓸 때마다 쟁점이 있음을 명시한다.
발견된 쟁점은 hypotheses.md의 "## 근거 쟁점" 섹션에 기록한다.
You MUST run this check BEFORE extracting — 모순된 근거 위에 가설을 세우지 않는다.
```

## Pass 1 — 경쟁사가 충족하지 못하는 것 찾기

### 1a. 서비스별 질문 (서비스 하나씩)

```
For EACH service in analysis/:
  - 이 서비스의 약점 → "이 약점을 우리가 해결하면 기회가 되는가?"
  - 이 서비스가 제공하지 않는 기능 → "없는데 우리 고객이 필요로 하는 것은?"
  - 가격 → "이 가격대에 대안이 없는 구간이 있는가?"
```

### 1b. 서비스 간 교차 비교 (여러 서비스를 한 번에)

```
모든 서비스를 하나의 표에 놓고 비교한다: 핵심 기능 × 가격 × 포지셔닝 × 가입 전 탐색 구조.
  "모든 서비스가 공통으로 안 하고 있는 것은?" → 시장 전체에 비어 있는 것의 후보
  "서비스 A는 하는데 B의 고객군에는 없는 것은?" → 특정 고객군이 놓치고 있는 것의 후보
개별 서비스 질문(1a)만으로는 시장 전체에 비어 있는 것이 보이지 않는다 — 이 비교를 생략하지 않는다.
```

### 1c. seed 확장 (우리 아이디어에서 출발하는 방향 탐색)

```
seed의 아이디어를 다음 확장 축으로 돌려본다. 최소 4개 축 검토:
  고객 확장 / 기능 확장 / 시장 확장 / 수익 모델 확장 / 제휴·파트너십 / 커뮤니티 / 기타
간접 경쟁·다른 접근 서비스에서 힌트를 얻는다:
  "이 서비스가 다른 고객에게 비슷한 문제를 풀고 있다면, 우리도 그 고객을 노릴 수 있는가?"
```

각 항목에 `출처(analysis·shots.md 인용) + seed와의 연결 + 유망도` 를 기록한다.
유망도 "높음"의 기준 = seed와 직접 연결 + 근거 확인 + 기존 기능·리소스로 커버 가능 (3조건 모두 충족).

## Pass 2 — 경쟁사가 잘하고 있어서 유저가 실제로 쓰는 것 찾기

당연해 보이는 것도 포함한다. 여기서 나오는 것이 검증된 니즈다.

```
For EACH service:
  Q1. 유저가 돈이나 시간을 쓰게 만드는 지점은 어디인가?
      (증거: 실제로 지불되는 가격, 리뷰에서 반복 언급되는 것, 계속 쓰게 만드는 장치, 성장 중인 기능)
  Q2. 그 지점이 충족하는 니즈는 무엇인가?
      기능 이름을 그대로 쓰지 말고 니즈 문장으로 번역한다:
        ✗ "독후감 제출 기능" → ✓ "진정성 있는 멤버만 있길 바라는 니즈"
        ✗ "지역 기반 탐색" → ✓ "이동 부담 없이 갈 수 있는 모임을 찾는 니즈"
  Q3. 당연해 보여도, 이것이 없으면 유저가 떠나는 기본기인가? (기본기 후보 태깅)
  Q4. 어느 화면·어느 위치에 구현되어 있나? — shots.md의 해당 캡처를 인용한다.
      (이 정보는 이후 placement 단계에서 "경쟁사는 이 기능을 어디에 뒀는가"의 참조가 된다)

Pass 2에서 찾은 니즈 목록은 hypotheses.md의 "## Pass 2 니즈 목록" 섹션에
번호를 붙여 기록한다. (기능 가설 카드가 "출처: Pass 2 니즈 N"으로 이 번호를 인용한다)
```

### 스킵 필터 — 공통 인프라 요소는 기록하지 않는다

```
다음은 어떤 서비스에나 들어가는 요소이므로 니즈로 기록하지 않는다:
  디자인 완성도·비주얼 품질, 로그인/회원가입/권한 관리, 결제 인프라,
  알림·설정 같은 범용 장치.

판별 기준: "이 문장을 경쟁 서비스가 아닌 아무 앱에 넣어도 성립하는가?"
  → 성립하면 기록하지 않는다.
  예: "가입이 편해야 한다" → 아무 앱에나 성립 → 기록 안 함
      "가입 전에 모임의 실제 분위기를 보고 싶다" → 이 도메인 고유 → 기록
```

## Phase 3 — 세 종류 가설로 정리

### 3a. 상위 기획 가설과 하위 기획 가설 도출

```
상위 기획 가설 (1~3개):
  seed의 고객·가치와 Pass 1/Pass 2 결과에서 수요 명제를 세운다.
  문장 형식: "사람들은(= seed의 고객은) {어떤 종류의} 모임/서비스를 원할 것이다"
  종류·대상이 구체적이어야 한다 (예: 자기개발형 모임, 지역 기반 모임, 인증형 모임).

하위 기획 가설 (3~7개):
  기능 가설 카드 후보들을 보면서 아래에서 위로 묻는다:
  "이 기능이 통하려면, 유저에 대해 무엇이 참이어야 하는가?"
  문장 형식: "{심리·니즈 조건}이 충족되어야/해소되어야 사람들이 {행동}할 것이다"
  예시가 되는 층위: 처음 가는 모임의 뻘쭘함에 대한 공포, 이상한 사람이 없다는 안전 보장,
  혼자서는 못 하니 약속의 강제력이 필요함, 시간을 낭비할까 봐 첫 참여를 망설임,
  모임 운영자는 반응이 와야 계속함.

주의: 이 두 종류의 가설은 화면 데이터만으로는 검증되지 않는 추론이 대부분이다.
  → 각 가설에 "근거 수준: 데이터 / 추론" 태그를 단다.
  → "추론" 태그가 붙은 가설은 사용자 검수(HITL) 또는 추가 조사의 우선 검토 대상이다.
```

### 3b. 기능 가설 카드 작성

Pass 1의 기회/영역 + Pass 2의 니즈 + seed를 통합해 카드로 재구성한다. 겹치는 항목은 병합한다.

```markdown
### 가설 N: {제목}

- 니즈: 사람들은 {상황}에서 {무엇}을 필요로 한다
- 가설: {우리가 X를 제공하면 | XX인 콘텐츠·기능에서} 유저 반응은 {Y}일 것이다
- 설명: {압축 1~3문장 — 왜 이 가설이 성립하는가}
- 근거: {analysis/{service}.md 인용 + screenshots/{service}/xxx.png 참조}
- 분류: 기본기 | 차별화 | 미검증
- 연결 가설: 상위 {N} / 하위 {N}
- 출처: Pass 1 기회 N | Pass 2 니즈 N | seed
- 검증 신호: {유저 반응을 측정할 수 있는 신호 — 예: 가입 전 콘텐츠 조회 → 가입 전환율}
```

### 정리 규칙

```
- "니즈" 문장은 반드시 수요측 진술이어야 한다 ("사람들은 ~을 필요로 한다").
  근거가 공급측뿐이면 — 즉 경쟁사가 만들어 놓았다는 사실만 있고 유저가 원한다는
  증거가 없으면 — 분류를 "미검증"으로 내리고 추가 조사 후보로 넘긴다.
  기능이 존재한다는 것과 유저가 원한다는 것은 다르다.

- 기본기 분류의 예외 규칙: 모든 직접 경쟁사가 채택했고 대규모 실사용이 확인되는 요소는,
  공급측 근거만으로도 수요가 입증된 것으로 본다 → "기본기"로 분류할 수 있다.
  (기본기의 근거는 성격상 공급측일 수밖에 없으므로, 이 예외가 없으면
   기본기 분류가 하나도 성립하지 않아 위의 강등 규칙과 모순된다)

- 분류가 우선순위 역할을 한다:
  기본기 = 없으면 지는 것 / 차별화 = 이기는 것 / 미검증 = 조사할 것.

- 모든 기능 가설 카드는 하위 기획 가설 최소 1개에 연결되어야 한다.
  연결할 하위 가설이 없으면 하위 가설을 새로 세우거나 카드를 버린다 —
  "왜 필요한지"가 없는 기능은 남기지 않는다.

- 카드 수 상한 12개 — 넘으면 seed와의 연결이 약한 것부터 버린다.
  이 단계의 목적은 아이디어를 늘리는 것이 아니라 압축하는 것이다.
```

## Phase 4 — Critic (1회)

```
Critic은 세 종류 가설 전체를 공격한다. 최소 5개 약점, 각각 어느 가설/카드인지 지목.

공격 관점 (모두 사용):
  비평가 관점 — 근거 없는 유저 반응 예측, 희망적 사고(wishful thinking), 톤 규칙 위반
  투자자 관점 — "이 니즈가 돈이 되는 크기인가? 유저가 지불한다는 증거가 있는가?"
  PM 관점 — "기능 이름을 니즈로 번역하지 않고 나열만 했는가? 스킵 필터 위반은 없는가?"

추가 공격 대상:
  - "쟁점" 태그가 붙은 근거를 쟁점 명시 없이 쓴 카드
  - 분류가 근거와 맞지 않는 카드 (수요측 증거 없이 "차별화"로 분류된 것 등)
  - 종류 배치 오류: 기능 수준의 내용이 하위 기획 가설 자리에 들어가 있거나,
    심리 명제가 기능 카드 자리에 들어가 있는 것
  - 연결이 없는 카드 / 어떤 카드에도 연결되지 않은 상위·하위 가설

Criteria: 인자가 주어지면 기본 공격 관점에 추가한다.
약점 목록과 각각을 어떻게 반영했는지는 hypotheses.md의 "## Critic 반영 기록"에 기록한다.
```

## Phase 5 — 반영 + 완성 조건 확인

```
Critic의 약점을 전부 반영한다 (수정/분류 하향/삭제 — 각각 사유 기록).

완성 조건:
  □ 상위 기획 가설 1~3개
  □ 하위 기획 가설 3~7개 (각각 근거 수준 태그 있음)
  □ 기능 가설 카드 7개 이상 (기본기 2개 이상, 차별화 3개 이상)
  □ 모든 카드에 니즈·가설·근거·분류·연결 가설·검증 신호가 있음
  □ 스킵 필터 위반 0건
  □ 추가 조사 필요 여부 판정 완료
미달 시: "최소 기준 미달: {항목}" 경고를 hypotheses.md 상단에 기록한다 (강제로 채우지 않는다).
```

## Phase 6 — 추가 조사 필요 판정 (모든 가설·카드 대상)

```
판정 대상: "미검증" 분류 카드(우선) + "추론" 태그가 붙은 상위·하위 가설
         + Pass 1에서 승계된 조사 항목.
각 대상에 대해 묻는다: "어떤 정보가 있으면 이 가설의 분류/판정이 바뀌는가?"
  판정을 바꿀 정보가 특정되면 → needs-research.md에 기록 (조사 방법 + 우선순위)
  특정되지 않으면 → 해당 카드에 "리스크로 기획서에 반영" 표시
기준: 판정을 실제로 바꿀 정보만 조사 항목이 된다. "알면 좋은 것"은 넣지 않는다.
```

