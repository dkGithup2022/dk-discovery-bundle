# 유사 서비스 분석 요소 가이드

## 중요도 분류 기준

```
중요: 이 정보가 없으면 이후 단계에서 비교/판단이 불가능.
      단계 3(브레인스토밍)에서 "우리가 뭘 다르게 할 수 있는가"를 판단하려면 상대가 뭘 하는지 알아야 한다.
      단계 4(BM 탐색)에서 "돈을 벌 수 있는가"를 판단하려면 시장의 가격/BM 구조를 알아야 한다.

애매: 있으면 분석이 풍부해지지만, 없어도 이후 단계의 핵심 판단은 가능.

참고만: 발견되면 기록하지만, 적극적으로 찾지 않아도 됨.
       이후 단계에서 직접 사용되지 않거나, 부차적 맥락만 제공.
```

---

## 중요 — 반드시 파악

### 1. 서비스가 말하는 핵심 가치 (Value Proposition)

**정의:** 서비스가 스스로 "우리는 이것을 제공한다"고 말하는 것.

**왜 필요한가:** 단계 3에서 "이 서비스의 가치 주장과 우리의 가치 주장이 겹치는가/다른가"를 비교하는 핵심 재료. 단계 5에서 우리의 가치 제안을 차별화하는 근거.

**어디서 찾는가:** 랜딩 페이지 히어로 섹션, 메타 description, Product Hunt 태그라인.

**기록 형식:** 원문 그대로 인용 + 한 줄 해석. 해석은 "이 서비스가 seed.md의 아이디어와 어떤 관계인가"를 한 줄로 판단하기 위함.

```
예시:
  원문: "The connected workspace for your docs, projects, & knowledge"
  해석: 문서/프로젝트/지식을 하나로 연결하는 워크스페이스
```

### 2. 핵심 고객군 (Target Customer)

**정의:** 이 서비스가 누구를 위해 만들어졌는가.

**왜 필요한가:** 단계 3에서 "같은 고객을 놓고 경쟁하는가, 다른 고객인가"를 판단. 같은 고객이면 직접 경쟁, 다른 고객이면 간접 참고.

**어디서 찾는가:** 랜딩 "For teams / For freelancers" 섹션, 가격 플랜명(Starter/Pro/Enterprise), 사례 페이지.

**기록 형식:** 고객 세그먼트 + 근거.

```
예시:
  고객: 중소기업 팀 (5-50명)
  근거: 가격 플랜이 Team($10/user)과 Business($25/user). Enterprise는 "Contact us".
```

### 3. 주요 기능 목록 (Core Features)

**정의:** 서비스가 제공하는 핵심 기능 3개 이상.

**왜 필요한가:** 단계 3에서 "기능 겹침/차이"를 매핑하는 핵심 재료. 단계 5에서 기능 범위를 정하는 근거.

**어디서 찾는가:** 랜딩 feature 섹션, 제품 페이지, 가격 기능 비교표.

**기록 형식:** 기능명 + 한 줄 설명.

```
예시:
  - 문서 편집: 블록 기반 에디터, 실시간 협업
  - 프로젝트 관리: 칸반, 타임라인, 스프린트
  - 위키: 팀 지식 베이스, 검색, 링크
```

### 4. 가격 모델 및 범위 (Pricing)

**정의:** 어떤 과금 방식이고, 얼마인가.

**왜 필요한가:** 단계 4에서 "시장 가격대가 어디인가", "우리가 어디에 위치할 수 있는가"를 판단하는 핵심.

**어디서 찾는가:** 가격 페이지 (pricing).

**기록 형식:**

```
예시:
  모델: 프리미엄 (무료 + 유료)
  구조: per-seat 월 구독
  범위: Free / Plus $10/user/mo / Business $25/user/mo / Enterprise (문의)
```

### 5. BM 구조 (Business Model)

**정의:** 이 서비스가 어떻게 돈을 버는가. 가격 모델보다 넓은 개념.

**왜 필요한가:** 단계 4(BM 탐색)의 핵심 입력.

**어디서 찾는가:** 가격 페이지, 블로그, 투자 기사, 인터뷰.

**기록 형식:**

```
예시:
  주 수익: SaaS 구독 (per-seat)
  부가 수익: AI 기능 추가 과금, 템플릿 마켓플레이스
  추정 규모: "ARR $100M 돌파" (시리즈B 기사) — 찾지 못하면 "N/A" 기록
```

참고: 비상장 스타트업은 매출을 공개하지 않는 경우가 많다. "추정 규모"는 기사/투자 정보에서 발견되면 기록하되, 찾지 못하면 "N/A"로 두고 다른 항목에 집중한다.

### 6. 강점 (Strengths)

**정의:** 이 서비스가 잘하는 것.

**왜 필요한가:** 단계 3에서 "이 서비스가 강한 곳을 우리가 정면 돌파할 것인가, 우회할 것인가"를 판단.

**어디서 찾는가:** 랜딩 페이지, G2/Capterra 긍정 리뷰.

**기록 형식:** 3개 이상 + 출처.

```
예시:
  1. 올인원 (문서+PM+위키) — G2에서 가장 많이 언급
  2. 블록 기반 유연성 — "뭐든 만들 수 있다"
  3. 무료 플랜이 넉넉 — 개인 사용자 유입 경로
```

### 7. 약점 / 유저 불만 (Weaknesses)

**정의:** 유저가 불만을 느끼는 점.

**왜 필요한가:** 단계 3에서 **"이 서비스의 약점이 우리의 기회인가"**를 판단하는 가장 중요한 재료 중 하나.

**어디서 찾는가:** G2/Capterra 1-3점 리뷰, Reddit 불만 스레드, Product Hunt 댓글.

**기록 형식:** 3개 이상 + 출처.

**수집 비용 안내:** 약점은 리뷰 사이트를 뒤져야 하므로 강점보다 도구 호출이 더 필요하다. 한 서비스당 약점 수집에 **최대 3회 도구 호출**을 허용한다 (WebSearch로 리뷰 검색 1회 + WebFetch/Playwright로 리뷰 페이지 접근 2회).

```
예시:
  1. 성능 — "페이지가 많아지면 느려진다" (G2 리뷰 다수)
  2. 학습 곡선 — "처음에 뭘 해야 할지 모르겠다" (Reddit r/Notion)
  3. 오프라인 미지원 — "인터넷 없으면 못 씀" (G2)
```

## 애매 — 있으면 좋음

### 8. 커뮤니티 인지도 (Community Presence)

**정의:** 유저/개발자 커뮤니티에서 얼마나 알려져 있는가.

**왜 필요한가:** 단계 3에서 "이 시장이 얼마나 성숙한가"를 가늠하는 보조 지표.

**어디서 찾는가:** G2 리뷰 수, Product Hunt upvote 수, Reddit 구독자, 앱스토어 다운로드.

**기록 형식:**

```
예시:
  G2: 4.7/5 (15,000+ reviews)
  Product Hunt: #1 Product of the Year 2023
  Reddit: r/Notion 200k+
```

### 9. UI/UX 특징 (Design & Interaction)

**정의:** 시각적 디자인 방향과 주요 인터랙션 패턴.

**왜 필요한가:** 현재 스코프는 "제공 가치 관점 기획서"까지이고, UX 기획은 이후 단계이므로 "애매"로 분류. UX 기획 단계까지 포함하는 경우에는 "중요"로 승격해야 한다.

**어디서 찾는가:** 랜딩 스크린샷, 데모 영상, Product Hunt, 앱스토어 프리뷰.

**기록 형식:**

```
예시:
  디자인 방향: 미니멀, 흑백 기반, 넓은 여백
  핵심 인터랙션: 블록 드래그앤드롭, 슬래시 커맨드
  특이점: 좌측 사이드바 트리 네비게이션
```

### 10. 서비스 규모 (Scale)

**정의:** 사용자 수, 추정 매출, 팀 크기.

**왜 필요한가:** 단계 4에서 시장 규모를 추정하는 보조 지표.

**어디서 찾는가:** 블로그(마일스톤), 투자 기사, LinkedIn, Crunchbase.

**기록 형식:**

```
예시:
  사용자: "100M+ users" (2024 블로그)
  팀: ~500명 (LinkedIn)
```

### 11. 차별화 포인트 (Differentiation)

**정의:** 경쟁사 대비 이 서비스만의 것.

**왜 필요한가:** 단계 3에서 "왜 유저가 이걸 선택하는가"를 이해하는 데 도움.

**어디서 찾는가:** 랜딩 "Why us" 섹션, vs 비교 페이지, G2 긍정 리뷰.

**기록 형식:** 한 줄 + 근거.

```
예시:
  차별화: "하나의 도구로 모든 것을 대체"
  근거: 랜딩 "Replace your cluttered tools" + G2 "replaced 5 tools" 리뷰
```

## 참고만 — 발견되면 기록

### 12. 기술 스택 (Tech Stack)

**정의:** 서비스가 어떤 기술로 만들어졌는가.

**왜 필요한가:** 이후 구현 단계에서 참고. 기획 단계에서는 직접 사용 안 됨.

**어디서 찾는가:** BuiltWith, 채용 페이지, 기술 블로그.

### 13. 투자 이력 (Funding History)

**정의:** 투자 라운드, 금액, 투자자.

**왜 필요한가:** 시장 투자 열기의 간접 지표.

**어디서 찾는가:** Crunchbase, 기사.

### 14. 런칭 시기 (Launch Date)

**정의:** 서비스 최초 공개 시점.

**왜 필요한가:** 시장 성숙도 보조 지표.

**어디서 찾는가:** About, Crunchbase, Product Hunt.
