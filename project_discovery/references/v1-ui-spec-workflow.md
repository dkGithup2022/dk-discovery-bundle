# UI Spec Workflow v1 — /dk-discovery-bundle:discovery-ui-spec

> **이 동작은 유저와의 대화가 본체인 단계입니다.**
> 두 번의 대화를 순서대로 진행합니다. 각 대화는 "초안 제시 → 유저가 빼고·더하고·고침 →
> 확정 → 다음 대화"로 굴러갑니다. 유저의 결정을 대신 내리지 마세요.
> 이 절차는 특정 서비스용이 아니라 **어떤 서비스 기획에도 쓰는 범용 절차**입니다 —
> 아래 예시는 예시일 뿐, 실제 내용은 항상 입력 문서에서 끌어냅니다.

가치 관점 기획(채택된 가설·가치·기능 방향이 정리된 문서)을 받아, **기능 목록과 전역 분위기**를
확정한다. 페이지 구성, 페이지별 배치, 페이지별 상세는 이 단계에서 정하지 않는다 —
다음 단계(discovery-sitemap → discovery-user-flow → discovery-wireframe)가 맡는다.

산출물은 두 곳의 입력이 된다:
- discovery-sitemap: 기능 목록 (핵심 1~N, 보조 s1~sN — 이 번호를 뒤 단계 전부가 그대로 쓴다)
- design-references: 전역 분위기 (사이트맵·와이어프레임을 기다리지 않고 바로 돌 수 있다)

## 입력

```
필수:
  기준 기획 문서 — 채택된 가치·기능 방향이 정리된 것 (이 파이프라인: value-proposal/seed-v2.md)
선택 (있으면 참조 강도가 올라감):
  가설 문서 — 각 기능의 검증 신호 (이 파이프라인: hypothesize/hypotheses.md)
  경쟁사 화면 자료 — 같은 기능을 경쟁사가 어떻게 제공하는지, 경쟁사의 분위기
    (이 파이프라인: research/screenshots/*/shots.md)
```

## 진행 구조 — 두 번의 대화

각 대화의 공통 규칙:
- 초안은 반드시 **입력 문서에서 도출**한다 (일반론으로 채우지 않는다)
- 유저가 빼고·더하고·묶고·쪼갠 결과를 확정본으로 삼고, ui-spec.md에 그 자리에서 기록한다
- 확정 없이 다음 대화로 넘어가지 않는다. 유저 결정 원문은 보존한다
- 대화가 길어지면 중단 가능 — ui-spec.md에 진행 상태를 남기고, Resume으로 재개한다
- 페이지 이야기가 나오면 결정 기록에 메모만 남기고 사이트맵 단계로 넘긴다 ("어느 화면에 둘까"는 여기서 정하지 않는다)
- 기능의 동작 규칙(누가 할 수 있나, 어떤 조건에서 막히나 — 예: "심사가 있는 모임만 가입 신청을 거친다")이
  나오면 "흐름 정책"에 적는다. 새 기능 번호를 붙이지 않는다. 이 단계에서 일부러 끌어내지는 않는다

### 대화 1 — 핵심 기능 나열 + 용어 확정

```
1-1. 서비스 용어를 먼저 확정한다:
  기준 기획 문서와 경쟁사 자료에 나오는 핵심 명사(예: 모임/이벤트/멤버)를 뽑아 제안한다.
  경쟁사 어휘를 그대로 가져오지 않는다 — 우리 서비스의 말로 유저가 고른다.
  확정한 용어는 뒤 단계 전부가 그대로 쓴다.

1-2. 기준 기획 문서의 채택된 가치·가설 하나하나에 대해 묻는다:
  "이것이 실제로 작동하려면, 유저(각 고객군)가 무엇을 할 수 있어야 하는가?"
당연한 것일수록 빠뜨리지 말고 적는다 — 이 목록의 목적은 참신함이 아니라 완전함이다.
기능은 유저 행동 수준으로 쓴다 ("~를 작성한다", "~없이 열람한다") — 시스템 구조 표현 금지.
각 기능에 출처(어느 가치/가설에서 나왔는지)와 주로 쓰는 고객군을 단다.

초안을 그룹으로 묶어 제시 → 유저 조정 → 확정. 확정 뒤 번호를 1부터 매긴다.
```

### 대화 2 — 보조 기능 나열 + 전역 분위기

```
2-1. 확정된 핵심 기능 각각에 대해 묻는다:
  "이 기능이 돌아가려면 뒤에서 무엇이 받쳐줘야 하는가?"
계정/가입, 알림, 검색, 온보딩, 신고·차단, 설정 같은 공통 요소가 여기서 들어온다.
  (주: 가설 단계에서는 이런 공통 요소를 니즈로 기록하지 않았지만 — 그건 차별화 판단용
   필터였다 — 기획 스펙에는 필요하다. 여기서 다시 포함한다.)
  (주: 유저 흐름 단계는 로그인·온보딩·검색 같은 흔한 흐름을 여기 있는 보조 기능만 그린다.
   필요한 공통 요소를 이 대화에서 빠뜨리면 흐름에서도 빠진다.)
핵심과 보조를 구분해 두는 이유: 뒤 단계에서 핵심 과업 흐름과 첫 묶음을 고르는 기준이 된다.
초안 제시 → 유저 조정 → 확정. 확정 뒤 번호를 s1부터 매긴다.

2-2. 전역 분위기를 정한다:
  서비스 전체의 톤을 한 문단으로 쓴다 — 누가 어떤 기분으로 쓰는 서비스인가, 무엇을 닮고
  무엇을 닮지 않는가. 색·폰트 같은 시각 결정은 하지 않는다 (디자인 단계의 일).
  경쟁사 자료가 있으면 "경쟁사 ○○의 분위기와 무엇이 다른가"를 함께 제시한다.
  필요하면 결이 다른 2안을 제시해 고르게 한다.
초안 제시 → 유저 조정 → 확정.
```

### ui-spec.md 구조

```markdown
# UI 기획 — {서비스 한 줄}

기준 문서: {입력 경로} · 진행 상태: 대화 {N}/2 완료

## 용어 (대화 1 확정)
| 쓰는 말 | 뜻 | 쓰지 않는 말 |

## 기능 목록
### 핵심 기능 (대화 1 확정)
| # | 기능 (유저 행동 수준) | 고객군 | 출처 (가치/가설) |
(번호: 1, 2, 3 …)
### 보조 기능 (대화 2 확정)
| # | 기능 | 받쳐주는 핵심 기능 |
(번호: s1, s2, s3 …)

## 전역 분위기 (대화 2 확정)
(한 문단)

## 흐름 정책
| # | 규칙 | 관련 기능 | 정한 곳 (대화 / 뒤 단계) |
(기능의 동작 규칙. 이 단계에서 나온 것이 없으면 "없음". 뒤 단계(사이트맵·유저 흐름·정합성 수정)에서
 정한 규칙도 여기에 더한다 — 기능 목록 다음으로 뒤 단계 전부가 기준으로 삼는 곳이다)

## 사이트맵 단계로 넘기는 메모
(대화 중 나온 페이지·배치 이야기. 결정이 아니라 참고 — 없으면 "없음")

## 결정 기록
| 대화 | 유저가 바꾼 것 (원문) |
```

## 완성 조건

```
□ 두 대화가 모두 유저 확정을 거침 (진행 상태 "대화 2/2 완료")
□ 핵심 기능 번호가 1부터 빈 번호 없이 이어지고, 보조 기능 번호가 s1부터 이어짐
□ 모든 핵심 기능에 고객군과 출처가 있고, 모든 보조 기능에 받쳐주는 핵심 기능이 있음
□ 기준 기획 문서의 채택된 가치·가설 중 기능이 하나도 나오지 않은 것 0
□ 용어 표가 있고, 기능 목록과 전역 분위기에 "쓰지 않는 말" 0
□ 전역 분위기 한 문단이 있고, 색·폰트 지정 0
□ 페이지 목록·페이지 배치를 확정한 곳 0 (메모로만 남김)
□ 유저 결정 원문 보존 (결정 기록)
□ 내부 용어·발명 조어 노출 0 (tone-guide 산출물 언어 규칙)
```
