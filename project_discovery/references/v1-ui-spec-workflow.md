# UI Spec Workflow v1 — /dk-discovery-bundle:discovery-ui-spec

> **이 동작은 유저와의 대화가 본체인 단계입니다.**
> 다섯 번의 대화를 순서대로 진행합니다. 각 대화는 "초안 제시 → 유저가 빼고·더하고·고침 →
> 확정 → 다음 대화"로 굴러갑니다. 유저의 결정을 대신 내리지 마세요.
> 이 절차는 특정 서비스용이 아니라 **어떤 서비스 기획에도 쓰는 범용 절차**입니다 —
> 아래 예시는 예시일 뿐, 실제 내용은 항상 입력 문서에서 끌어냅니다.

가치 관점 기획(채택된 가설·가치·기능 방향이 정리된 문서)을 받아, UI 없이 **글로만** 쓴
UI 기획서를 만든다: 무슨 기능이 있고, 어떤 페이지들로 나뉘고, 각 페이지가 무엇을 담고
어떤 분위기·배치인지. 산출물은 디자인 단계(시안 제작)의 직접 입력이 된다.

## 입력

```
필수:
  기준 기획 문서 — 채택된 가치·기능 방향이 정리된 것 (이 파이프라인: value-proposal/seed-v2.md)
선택 (있으면 참조 강도가 올라감):
  가설 문서 — 각 기능의 검증 신호 (페이지의 성공 신호로 승계)
  경쟁사 화면 자료 — 같은 기능을 경쟁사는 어느 화면 어디에 뒀는지
    (이 파이프라인: 가설의 화면 위치 기록 + screenshots/*/shots.md)
```

## 진행 구조 — 다섯 번의 대화

각 대화의 공통 규칙:
- 초안은 반드시 **입력 문서에서 도출**한다 (일반론으로 채우지 않는다)
- 유저가 빼고·더하고·묶고·쪼갠 결과를 확정본으로 삼고, ui-spec.md에 그 자리에서 기록한다
- 확정 없이 다음 대화로 넘어가지 않는다. 유저 결정 원문은 보존한다
- 대화가 길어지면 중단 가능 — ui-spec.md에 진행 상태를 남기고, Resume으로 재개한다

### 대화 1 — 핵심 기능 나열

```
기준 기획 문서의 채택된 가치·가설 하나하나에 대해 묻는다:
  "이것이 실제로 작동하려면, 유저(각 고객군)가 무엇을 할 수 있어야 하는가?"
당연한 것일수록 빠뜨리지 말고 적는다 — 이 목록의 목적은 참신함이 아니라 완전함이다.
기능은 유저 행동 수준으로 쓴다 ("~를 작성한다", "~없이 열람한다") — 시스템 구조 표현 금지.
각 기능에 출처(어느 가치/가설에서 나왔는지)를 단다.

초안을 그룹으로 묶어 제시 → 유저 조정 → 확정.
```

### 대화 2 — 보조 기능 나열

```
확정된 핵심 기능 각각에 대해 묻는다:
  "이 기능이 돌아가려면 뒤에서 무엇이 받쳐줘야 하는가?"
계정/가입, 알림, 검색, 온보딩, 신고·차단, 설정 같은 공통 요소가 여기서 들어온다.
  (주: 가설 단계에서는 이런 공통 요소를 니즈로 기록하지 않았지만 — 그건 차별화 판단용
   필터였다 — 기획 스펙에는 필요하다. 여기서 다시 포함한다.)
핵심과 보조를 구분해 두는 이유: 뒤 단계에서 우선순위를 정할 때 기준이 된다.

초안 제시 → 유저 조정 → 확정.
```

### 대화 3 — 페이지 나열

```
확정된 기능 전체(핵심+보조)를 보고 페이지 목록을 제안한다:
  - 페이지마다 한 줄 역할 (어떤 가치/기능을 담당하는가)
  - 내비게이션 구조 (탭/메뉴 — 유저가 어떻게 오가는가)
  - 경쟁사 화면 자료가 있으면: 경쟁사들의 페이지 구성을 비교 참조로 함께 제시
필요하면 구성이 다른 2안을 제시해 고르게 한다.

초안 제시 → 유저 조정 → 확정.
```

### 대화 4 — 페이지별 기능 배치

```
확정된 기능 목록 × 확정된 페이지 목록의 배치표를 제안한다:
  - 모든 기능이 최소 한 페이지에 배치되어야 한다 (미배치 기능 = 표에서 즉시 보이게)
  - 한 기능이 여러 페이지에 걸치면 어느 쪽이 주 무대인지 표시
  - 경쟁사 화면 자료가 있으면: "경쟁사 ○○는 이 기능을 △△ 화면에 뒀다"를 근거로 첨부

배치표 제시 → 유저 조정 → 확정.
```

### 대화 5 — 구멍 메우기 + 페이지별 상세

```
5-1. 구멍 점검을 함께 한다:
  - 미배치 기능 / 기능이 없는 페이지가 남았는가
  - 고객군별로 걸어보기: 각 고객군의 대표 시나리오(처음 온 사람, 핵심 행동을 하는 사람,
    운영하는 사람 등)를 페이지 흐름으로 따라가며 끊기는 곳을 찾는다
  - 끊기는 곳 = 빠진 페이지 또는 빠진 기능 → 유저와 함께 추가 결정

5-2. 페이지별 상세를 쓴다 (전부 글로):
  - 전역 분위기 1회: 서비스 전체의 톤을 한 문단으로 (유저와 합의)
  - 페이지마다:
    · 역할: 어떤 가치를 실현하는 페이지인가
    · 담는 기능: 배치표에서 승계
    · 분위기: 전역과 다른 점만
    · 구성과 위치: 상단/중단/하단 순으로 무엇이 오는지 글로
    · 경쟁사 참조: 참조했다면 무엇을 왜 따르고/달리했는지
    · 성공 신호: 이 페이지가 일하고 있다는 걸 무엇으로 아는가 (가설의 검증 신호 승계)
  상세 초안 제시 → 유저 조정 → 확정. 페이지가 많으면 중요한 것부터 묶음으로 진행.
```

### ui-spec.md 구조

```markdown
# UI 기획 — {서비스 한 줄}

기준 문서: {입력 경로} · 진행 상태: 대화 {N}/5 완료

## 전역 분위기
(한 문단)

## 기능 목록
### 핵심 기능 (대화 1 확정)
| # | 기능 (유저 행동 수준) | 출처 (가치/가설) |
### 보조 기능 (대화 2 확정)
| # | 기능 | 받쳐주는 핵심 기능 |

## 페이지 구성 (대화 3 확정)
| 페이지 | 역할 한 줄 |
내비게이션: (글로)

## 페이지별 기능 배치 (대화 4 확정)
| 기능 | 페이지 | 주 무대 | 경쟁사 참조 |

## 페이지별 상세 (대화 5 확정)
### 페이지: {이름}
- 역할 / 담는 기능 / 분위기(차이점만) / 구성과 위치 / 경쟁사 참조 / 성공 신호

## 결정 기록
| 대화 | 유저가 바꾼 것 (원문) |
```

## 완성 조건

```
□ 다섯 대화가 모두 유저 확정을 거침 (진행 상태 기록)
□ 모든 핵심 기능이 페이지에 배치됨 (미배치 0)
□ 모든 페이지에 역할·구성·성공 신호가 있음
□ 고객군별 대표 시나리오가 페이지 흐름에서 끊기지 않음 (대화 5-1 점검 완료)
□ 유저 결정 원문 보존 (결정 기록)
□ 내부 용어·발명 조어 노출 0 (tone-guide 산출물 언어 규칙)
```
