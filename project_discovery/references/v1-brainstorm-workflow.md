# Brainstorm Workflow v1 — /dk-discovery-bundle:discovery-brainstorm

> **이 동작은 에이전틱(agentic)한 동작입니다.**
> 아래의 명령을 수행하되, 한 번의 생성으로 끝내지 마세요.
> "완성 조건" 체크리스트를 기준으로 스스로 점검하고,
> 미달 항목이 있으면 해당 작업으로 돌아가 다시 수행하는 식으로,
> **완성될 때까지 반복적으로 LLM 호출(생성→점검→수정)을 이어가 답을 도출하세요.**

research(경쟁 서비스 분석)와 service-recording(경쟁 서비스 화면 기록)의 산출물을
seed(우리 아이디어)와 대조하여, 다음 단계인 v1-hypothesize(가설 추론)가 쓸 세 가지 재료를 만든다:

1. **기회 목록** — 경쟁사가 충족하지 못하는 것에서 나온 사업 기회
2. **가능 영역 목록** — 우리 아이디어에서 출발해 갈 수 있는 사업 방향과 고객군
3. **추가 조사 항목** — 유망해 보이지만 검증 데이터가 부족한 것

## 용어 정의 (이 문서에서 쓰는 용어 — 먼저 읽을 것)

| 용어 | 정의 |
|------|------|
| 기회 | 경쟁사의 약점, 제공하지 않는 기능, 비어 있는 가격대에서 도출한 사업 기회. 세 유형으로 분류한다: 경쟁사 약점 기회 / 시장 전체에 비어 있는 것 / 특정 고객군이 놓치고 있는 것 |
| 가능 영역 | seed의 아이디어를 확장 축(고객·기능·시장·수익 모델·제휴·커뮤니티 등)으로 돌려서 나온, 원래 생각하지 않았던 방향 |
| 유망도 | 각 기회/영역이 얼마나 추진할 만한가의 판정. 높음/중간/낮음. "높음" = seed와 직접 연결 + 근거 확인 + 기존 기능·리소스로 커버 가능 (3조건 모두 충족) |
| 근거 쟁점 | analysis 문서의 주장과 스크린샷 기록이 서로 모순되는 항목 |

## 참조 레퍼런스

```
You MUST read these before starting:
  tone-guide.md — 톤 가이드 (증거가 말하게 하라)
  git/git-verification.md — 커밋 규칙 (커밋 메시지 prefix는 discovery, 커밋 전 staged 파일 검증)
```

## 입력

```
You MUST load ALL of:
  init/seed.md — 아이디어·고객·가치 (모든 판단의 기준점)
  research/references.md — 경쟁 서비스 목록 + 분류 (직접/간접/다른 접근)
  research/analysis/{service}.md — 전부 (서비스별 강점·약점·가격·수익 모델)
  research/screenshots/{service}/shots.md — 전부 (화면 캡처의 캡션 + URL)
```

## 근거 정합성 체크 (읽기 직후, 작업 시작 전)

```
analysis 문서의 주장과 shots.md의 화면 기록을 대조한다.
  모순 발견 시 (예: analysis에는 "가입 전 정보가 부족하다"라고 쓰여 있는데
  실제 화면 캡처에는 멤버 수·일정·게시판이 공개되어 있는 경우):
    → 화면 기록을 우선한다. 직접 관찰한 것이 간접 수집한 것보다 신뢰도가 높다.
    → 해당 항목에 "쟁점: analysis와 화면 기록 불일치 — {내용}" 태그를 달고,
      이후 이 항목을 근거로 쓸 때마다 쟁점이 있음을 명시한다.
발견된 쟁점은 brainstorm.md의 "## 근거 쟁점" 섹션에 기록한다.
You MUST run this check BEFORE the tasks — 모순된 근거 위에 기회를 세우지 않는다.
```

## 작업 1 — 서비스별 질문 (서비스 하나씩)

```
For EACH service in analysis/:
  - 이 서비스의 약점 → "이 약점을 우리가 해결하면 기회가 되는가?"
  - 이 서비스가 제공하지 않는 기능 → "없는데 우리 고객이 필요로 하는 것은?"
  - 가격 → "이 가격대에 대안이 없는 구간이 있는가?"
```

## 작업 2 — 서비스 간 교차 비교 (여러 서비스를 한 번에)

```
모든 서비스를 하나의 표에 놓고 비교한다: 핵심 기능 × 가격 × 포지셔닝 × 가입 전 탐색 구조.
  "모든 서비스가 공통으로 안 하고 있는 것은?" → 시장 전체에 비어 있는 것의 후보
  "서비스 A는 하는데 B의 고객군에는 없는 것은?" → 특정 고객군이 놓치고 있는 것의 후보
개별 서비스 질문(작업 1)만으로는 시장 전체에 비어 있는 것이 보이지 않는다 — 이 비교를 생략하지 않는다.
```

## 작업 3 — seed 확장 (우리 아이디어에서 출발하는 방향 탐색)

```
seed의 아이디어를 다음 확장 축으로 돌려본다. 최소 4개 축 검토:
  고객 확장 / 기능 확장 / 시장 확장 / 수익 모델 확장 / 제휴·파트너십 / 커뮤니티 / 기타
간접 경쟁·다른 접근 서비스에서 힌트를 얻는다:
  "이 서비스가 다른 고객에게 비슷한 문제를 풀고 있다면, 우리도 그 고객을 노릴 수 있는가?"
```

## 기록 규칙 (작업 1~3 공통)

```
각 기회/영역에 반드시 기록한다:
  - 출처: analysis/{service}.md 인용. 화면에서 확인된 것은 screenshots/{service}/xxx.png도 인용
    (화면 근거는 특히 "가입 전 탐색 구조" 같은 UX 관련 주장에서 강력하다)
  - seed와의 연결: 우리 아이디어/고객/가치와 어떻게 연결되는가
  - 유망도: 높음/중간/낮음 + 이유 (용어 정의의 3조건 기준)
"쟁점" 태그가 붙은 근거를 쓸 때는 쟁점을 함께 명시한다.
```

## 작업 4 — 추가 조사 항목 식별

```
각 기회/영역에 대해 묻는다: "이것을 검증하려면 어떤 정보가 더 필요한가?"
  이미 가진 데이터로 판단 가능 → 추가 조사 불필요
  판단을 바꿀 정보가 특정됨 → needs-research.md에 기록 (조사 방법 + 우선순위)
기준: 유망도 판정을 실제로 바꿀 정보만 조사 항목이 된다. "알면 좋은 것"은 넣지 않는다.
```

## Critic (1회)

```
Critic은 결과 전체를 공격한다. 최소 5개 약점, 각각 어느 기회/영역인지 지목.

공격 관점 (모두 사용):
  비평가 관점 — 근거 없는 주장, 희망적 사고(wishful thinking), 과잉 일반화
    (특히: 일부 서비스에만 해당하는 것을 "시장 전체에 없다"고 쓴 것)
  투자자 관점 — "이 기회가 돈이 되는 크기인가? 유저가 지불한다는 증거가 있는가?"
  PM 관점 — "기회가 구체적인가, '성능 문제' 수준의 뭉뚱그림인가? 유망도가 3조건 기준에 맞는가?"

추가 공격 대상:
  - "쟁점" 태그가 붙은 근거를 쟁점 명시 없이 쓴 항목
  - seed와의 연결이 적혀 있지 않거나 억지인 항목

Criteria: 인자가 주어지면 기본 공격 관점에 추가한다.
약점 목록과 반영 내역은 brainstorm.md의 "## Critic 반영 기록"에 기록한다.
```

## 완성 조건

```
Critic의 약점을 전부 반영한 뒤 확인한다:
  □ 기회 5개 이상 (각각 근거·seed 연결·유망도 포함)
  □ 가능 영역 3개 이상 (최소 4개 확장 축 검토의 결과)
  □ 서비스 간 교차 비교 수행됨 (작업 2 생략 없음)
  □ 모든 항목에 유망도 판정 (높음/중간/낮음 + 이유)
  □ 추가 조사 필요 여부 판정 완료
미달 시: 해당 작업으로 돌아가 보강한다. 보강 불가하면
"최소 기준 미달: {항목}" 경고를 brainstorm.md 상단에 기록한다.
```

## Commit

```
git add brainstorm/ 산출물만

```
