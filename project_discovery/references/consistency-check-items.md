# 정합성 검사 항목 — 무엇을 모순·누락으로 보는가

discovery-consistency-check가 찾고 discovery-consistency-fix가 고치는 문제의 목록이다.
항목은 예시 run(크루 매거진 커뮤니티 앱)에서 사이트맵·유저 흐름·와이어프레임을 실제로 돌렸을 때
나온 문제에서 뽑았다. 각 항목의 "실제 사례"가 그 근거다.

## 왜 이 단계가 필요한가

사이트맵 → 유저 흐름 → 와이어프레임으로 내려갈수록 화면이 구체해지고, 앞 단계에서 보이지 않던
모순과 빈칸이 드러난다. 각 단계는 자기 앞 단계만 대조하므로, 세 단계를 건너뛰어 생긴 모순
(예: 와이어프레임의 버튼이 seed-v2의 핵심 가치와 어긋남)은 아무도 잡지 않는다.
이 단계는 기획 문서 전체를 한자리에 놓고 대조해, 클로드 디자인으로 넘기기 전에 문서끼리 같은 말을 하게 만든다.

클로드 디자인은 기획 문서를 기준으로 그린다. 문서끼리 모순이 있으면 디자인이 둘 중 하나를 조용히 고르고,
그 선택은 시안에만 남는다. 그래서 구조의 모순은 여기서 고친다.
화면을 눈으로 봐야 드러나는 문제(정보 밀도, 카드 모양의 중복 등)는 이 단계의 대상이 아니다.

## 판단 기준이 되는 곳 — 결정 기록

이전 세션의 대화는 다음 세션으로 이어지지 않는다. 유저가 무엇을 정했는지는 문서에 남은 것만 믿는다:

```
seed-v2.md 부록 결정 기록 · ui-spec.md 결정 기록 · sitemap.md 결정 기록
user-flow.md 결정 기록 · wireframe.md 결정 기록 · 각 단계 handoff.json · git log의 discovery(...) 커밋 메시지
```

두 문서가 다른 말을 하면, 결정 기록에 유저 원문이 있는 쪽을 기준으로 본다.
앞 단계 문서(seed-v2, ui-spec)도 고칠 대상이다. 다른 스킬의 산출물이라도 뒤 결정과 어긋나면 문제로 올린다
(실제 사례: seed-v2 고객군 이름 "크루 운영자"를 ui-spec 결정에 맞춰 고쳤다).
둘 다 유저 원문이 있으면 나중 것을 기준으로 보되, 문제로 올려 유저에게 확인한다.
"테스트 실행 — 대리 확인"이나 "유저 확인 전 초안"으로 표시된 결정은 유저 결정으로 보지 않는다.

## 문제의 종류

| 종류 | 뜻 |
|------|-----|
| 모순 | 두 문서(또는 한 문서의 두 곳)가 같은 대상에 대해 다른 말을 한다 |
| 누락 | 한 문서가 요구하거나 넘긴 것을 받을 곳이 뒤 문서에 없다 |
| 미결 | 유저 결정이 필요한데 아직 결정 기록에 없다 (대리 확인, 조건 미정, 확인 필요 포함) |

## 검사 항목

항목마다 무엇으로 확인하는지 붙어 있다:
`[스크립트]` 문서 글자를 세거나 대조한다 · `[브라우저]` wireframe.html을 열어 좌표를 잰다 · `[눈]` 원문을 읽고 판단한다.
스크립트·브라우저 결과도 문제로 올리기 전에 눈으로 한 번 거른다.

### A. 결정 기록과 어긋남

```
A1. [스크립트+눈] 서비스 용어: 결정 기록에서 쓰지 않기로 한 말이 산출물에 남아 있다
    실제 사례: ui-spec 대화 5에서 "크루"를 쓰지 않기로 했는데, seed-v2 고객군 이름 "크루 운영자"가
    유저 흐름의 "누가" 칸으로 넘어왔다
A2. [눈] 확정된 구조: 결정 기록에 확정된 탭·흐름 정책·공개 범위 등과 다른 내용이 뒤 단계에 있다
A3. [눈] 채택하지 않은 것: seed-v2의 "채택하지 않은 것"(보류·제외)이 뒤 단계에 기능·섹션으로 들어와 있다
```

### B. 번호와 참조

```
B1. [스크립트] 기능 번호: ui-spec의 기능 번호가 사이트맵·흐름·와이어프레임에서 다른 기능을 가리키거나,
    삭제된 번호(취소선)가 뒤 단계에 쓰였다
B2. [스크립트] 페이지·섹션 번호: 사이트맵이 바뀐 뒤 흐름·와이어프레임이 옛 번호를 가리킨다
    실제 사례: 섹션 P11-3을 중간에 넣어 3~6이 4~7로 밀렸고, 다른 표의 참조를 모두 손으로 고쳐야 했다
B3. [스크립트] 흐름 번호: 와이어프레임의 와이어플로·상태 화면이 없는 흐름 번호나 노드를 가리킨다
```

### C. 이동

```
C1. [스크립트+눈] 이동 표 양쪽 불일치: A 줄 "나가는 곳"에 B가 있으면 B 줄 "들어오는 곳"에 A가 있어야 한다 (반대도)
    실제 사례: P4 줄 나가는 곳에 X1이 없는데 X1 줄 들어오는 곳에는 P4-4·P4-5가 있었다
    세지 않는 이동 (user-flow-guide.md "이동 표와 대조할 때 따로 대조하지 않는 이동"과 같다):
      모달·드로어 닫기, 1층 메뉴(앱이면 하단 탭)끼리의 이동, 뒤로 가기,
      "들어온 곳으로 복귀"처럼 출발지가 정해지지 않은 돌아가기
    (테스트 실행에서 이것들을 셌더니 1·2회차 모두 같은 11건이 나왔고, 문제는 그중 0건이었다)
C2. [스크립트+눈] 흐름에 쓰인 이동이 이동 표에 없다 / 이동 표의 이동을 일으키는 행동이 섹션에 없다
```

### D. 행동을 누를 요소

```
D1. [스크립트+눈] 흐름의 유저 입력(누른다, 입력한다)을 할 요소가 그 화면의 섹션 목록에 없다
    (섹션이 있는지는 스크립트로, 그 섹션에 누를 요소가 있는지는 "담는 내용"을 읽어 눈으로)
    실제 사례: 바텀시트 모달 M1·M2·M3·M5에 닫기 요소가 없었다. X1-2에 인증번호 받기 버튼이 없었다
D2. [눈] 근거 없는 요소: 와이어프레임의 요소가 사이트맵 섹션의 "담는 내용"에 근거가 없다,
    또는 사이트맵 "담는 내용"의 요소가 ui-spec 기능 목록에 근거가 없다 (지어낸 요소)
    실제 사례: 사이트맵 더보기 메뉴의 "공유"가 ui-spec 어느 기능에도 없었다
```

### E. 목적과 화면의 어긋남

```
E1. [브라우저+눈] 페이지의 핵심 행동(와이어프레임에서 강조한 버튼)이 사이트맵 페이지 목록의 "목적 한 줄"과 다르다
    실제 사례: P5 모임 페이지 목적은 가입 결정인데 강조 버튼이 "팔로우"로 채워졌다.
    P9 모집 글 목적은 가입 신청인데 "모임 페이지로 가기"가 채워졌다
E2. [브라우저+눈] seed-v2의 핵심 가치가 어느 페이지의 첫 화면(첫 화면 경계 위)에도 나타나지 않는다
E3. [브라우저] 화면에 고정되는 섹션(하단 탭 바, 하단 고정 버튼 바)이 첫 화면 경계 아래에 그려져 있다
    실제 사례: P4 "화면 하단 고정" 반응 바가 긴 페이지 맨 아래에 그려져 첫 화면에 보이지 않았다
E4. [눈] 화면에 미리 보이는 조건(정원 마감, 심사 대기, 권한 없음)을 흐름이 "누른 뒤의 결과"로 그렸다
    — 버튼이 이미 막혀 보이는데 흐름은 누른 다음에 확인한다
    실제 사례: 정원 마감 버튼을 그렸는데 F4는 신청을 누른 뒤에 정원을 확인했다
```

### F. 넘긴 것을 받을 곳

```
F1. [눈] 앞 단계가 "뒤 단계에서 정한다/묻는다"고 넘긴 항목을 뒤 단계 문서가 다루지 않았다
    실제 사례: 유저 흐름이 조건 미정 21가지를 "와이어프레임에서 다시 묻는다"고 넘겼지만,
    와이어프레임 워크플로에는 조건을 묻는 자리가 없어 메모로만 옮겨졌다
F2. [스크립트+눈] 뒤 단계에서 새로 생긴 기능·페이지가 앞 단계 문서(ui-spec 기능 목록, sitemap 페이지 목록)에 없다
    실제 사례: 사이트맵이 ui-spec에 없던 페이지 16개(목록에서 들어가는 상세·입력 화면)를 추가했다
```

### G. 확인되지 않은 결정

```
G1. [스크립트+눈] "테스트 실행 — 대리 확인", "유저 확인 전 초안", "확인 필요", "조건 미정"으로 남은 항목
    — 모두 미결로 올리되 두 갈래로 나눈다:
      화면이나 기능을 바꾸는 대리 결정 (누가 무엇을 할 수 있는가, 공개 범위, 가입 방식, 정원 같은 서비스 정책)
        → 하나씩 따로 올린다. 유저가 하나씩 정해야 하는 것이다
      과정 기록 (첫 묶음 선택, 플랫폼 기본값, 아티팩트 생략, 트리 밖 배치처럼 구조·진행에 관한 대리 확인)
        → 문서마다 한 문제로 묶어 올린다. 근거 칸에는 원문 대신 위치 목록을 적는다
    실제 사례: 대리 확인이 40곳 가까이 있었다. 정책 5건은 따로, 나머지는 한 묶음(R1-18)으로 올렸다
```

### H. 표기

```
H1. [스크립트] 화면 상태 표기가 정해진 이름과 다르다 (" · " 뒤에 여섯 가지 상태가 아닌 글자)
H2. [스크립트] mermaid 파싱이 깨지는 표기 (괄호가 든 노드 글자를 따옴표로 감싸지 않음)
H3. [스크립트+눈] 같은 대상을 문서마다 다른 이름으로 부른다 (예: "X1 로그인" / "X1 로그인·가입")
```

### I. 생성기와 손수정

```
I1. [스크립트] wireframe/.gen/ 그림 데이터로 다시 만든 wireframe.html·wireframe.md가 커밋본과 다르다
    — 누군가 HTML이나 md를 손으로 고쳤다는 뜻이다. 다음 생성 때 그 수정이 사라진다.
    입력 문서를 건드리지 않도록 run 사본(scratchpad)에서 돌린다
```

## 대상 밖

```
- 화면을 눈으로 봐야 판단할 수 있는 것 (정보 밀도, 시각 위계, 카드 모양이 비슷함) — 클로드 디자인 뒤에 본다
- 스킬 문서 자체의 결함 (예: 규칙끼리 충돌) — 산출물에 나타난 결과만 문제로 올리고,
  스킬 결함이 원인이면 "원인: 스킬 규칙 {문서·위치}"로 적어 둔다
- 조사·가설 단계(research, hypothesize)의 내용 판단 — 이 단계는 seed-v2 이후 문서만 대조한다
```
