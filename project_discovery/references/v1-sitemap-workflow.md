# Sitemap Workflow v1 — /dk-discovery-bundle:discovery-sitemap

> **이 동작은 에이전틱(agentic)한 동작이며, 두 지점에서 유저 확인을 받습니다.**
> 아래의 명령을 수행하되, 한 번의 생성으로 끝내지 마세요.
> "완성 조건" 체크리스트를 기준으로 스스로 점검하고,
> 미달 항목이 있으면 해당 단계로 돌아가 다시 수행하는 식으로,
> **완성될 때까지 반복적으로 LLM 호출(생성→점검→수정)을 이어가 답을 도출하세요.**
> 단, "유저 확인" 표시가 있는 두 지점(1층 확정, 전체 확인)에서는 유저의 결정을 대신 내리지 마세요.

확정된 기능 목록을 받아 **사이트맵**을 만든다: 서비스에 어떤 페이지가 있고, 어떻게 묶이고,
각 페이지가 위에서 아래로 어떤 섹션으로 이루어지고, 어느 페이지에서 어느 페이지로 갈 수 있는지.
산출물은 다음 단계인 유저 흐름과 와이어프레임의 직접 입력이 된다 — 두 단계 모두
이 문서의 페이지 번호로 페이지를 가리킨다.

이 스킬은 두 가지로 실행된다:
- **처음 만들기** — sitemap.md가 없을 때. 아래 "진행 순서" 0~8단계를 그대로 간다.
- **다시 만들기** — sitemap.md가 이미 있고, 유저 흐름이나 와이어프레임 단계가
  "discovery-sitemap 재실행"으로 정한 추가 후보를 넘겼을 때. 아래 "다시 만들기" 절을 따른다.
  뒤 단계가 이미 이 문서의 번호를 쓰고 있으므로 **기존 번호를 바꾸지 않는 것**이 가장 중요한 규칙이다.

## 진행 순서

### 0. 재료 읽기와 전제 확인

```
- sitemap/sitemap.md가 이미 있으면 처음 만들기를 하지 않는다:
    user-flow.md나 wireframe.md의 진행 상태가 "사이트맵 재실행 대기"이거나 Candidates: 인자가 있으면 → "다시 만들기" 절로 간다
    그렇지 않으면 → 유저에게 "고칠 부분이 있는지, 처음부터 다시 할지" 묻는다. 처음부터 다시 하면
      유저 흐름·와이어프레임이 쓰던 번호가 깨질 수 있다고 함께 알린다
    대화형이 아니면 묻지 않고 기존 파일을 건드리지 않은 채 멈춘다
- 입력 문서를 모두 읽는다.
- 서비스 용어를 확인한다. ui-spec에 용어 표가 있으면 그대로 쓰고, 없으면 기능 목록에
  나오는 핵심 명사(예: 모임, 이벤트)를 추려 유저에게 확인한다 — 페이지 이름에 그대로 쓰이기 때문이다.
- 플랫폼을 확인한다: 웹 / 앱 / 둘 다. Platform: 인자나 seed-v2에 없으면 웹으로 두고, 결정 기록에 그렇게 적는다.
  1층이 상단 메뉴가 될지(웹) 하단 탭이 될지(앱)가 여기서 갈린다. 둘 다이면 웹 기준으로 만든다.
```

### 1. 기능을 페이지로 묶기

```
기능을 "유저가 머무는 장소" 단위로 묶어 페이지 후보를 만든다.
  - 한 페이지에는 목적 하나만 둔다. 목적을 한 줄로 쓸 수 없으면 나눈다
  - 같은 틀로 여러 개 생기는 페이지는 템플릿 하나로 둔다
  - 보조 기능(로그인, 알림, 설정 등)도 빠짐없이 페이지 후보에 넣는다
각 페이지 후보에 목적 한 줄과 담는 기능 번호를 적는다.
```

### 2. 페이지 유형 나누기

```
각 페이지 후보에 유형을 붙인다: 페이지 / 상세 / 모달 / 드로어 / 트리 밖 (sitemap-guide.md "페이지 유형".
앱이면 같은 문서의 대응표대로 탭 / 상세 / 모달 / 트리 밖)
트리 밖과 모달·드로어는 이 시점에 번호를 붙여 분리해 둔다 (X1…, M1…).
```

### 3. 1층(주 내비게이션) 정하기 — 유저 확인 1

```
핵심 가치와 고객군별 핵심 과업을 기준으로 1층을 3~5개 제안한다.
  - 1층마다: 이름, 목적 한 줄, 어느 고객군의 어떤 과업을 위한 것인지
  - 경쟁사 자료가 있으면: 경쟁사들의 메뉴 구성을 비교표로 함께 제시 (출처: shots.md 파일명)
  - 판단이 갈리면 구성이 다른 2안을 제시해 고르게 한다
유저가 확정하기 전에 4단계로 넘어가지 않는다.
  1층은 나머지 전체의 뼈대라서, 뒤에서 바뀌면 4~6단계를 전부 다시 해야 한다.
유저 결정 원문은 결정 기록에 보존한다.
```

### 4. 나머지 페이지를 트리에 매달기

```
1층이 아닌 페이지 각각의 부모를 정한다. 부모 = 그 페이지에 가장 주로 들어오는 곳.
확정된 페이지에 번호를 붙인다 (P1…). 트리 그림(mermaid)을 그린다.
웹이면 페이지마다 URL 경로를 정한다 (sitemap-guide.md "URL 경로").
페이지를 가로지르는 이동은 이 그림에 그리지 않는다 — 6단계의 이동 표에 적는다.
```

### 5. 페이지별 섹션 목록 쓰기

```
페이지마다 위에서 아래 순서로 섹션을 적는다.
  - 섹션마다: 이름, 담는 내용 한 줄, 담는 기능 번호
  - 여러 페이지에 반복되는 섹션(상단 메뉴, 푸터. 앱이면 하단 탭)은 [공통]으로 표시하고,
    "공통 섹션" 표에서 한 번만 정의한다
  - 경쟁사의 같은 성격 페이지가 있으면 그 섹션 구성을 참고로 붙인다 (출처 명시)
이 단계에서 모든 기능 번호가 어느 섹션에든 들어가야 한다.
```

### 6. 이동 표 쓰기

```
페이지마다 들어오는 곳과 나가는 곳을 적는다 (페이지 번호로).
트리의 부모→자식 이동도 포함한다 — 이 표가 이동의 전체 목록이다.
트리 밖 페이지와 모달은 어떤 행동이 그 페이지를 부르는지 함께 적는다
  (예: X1 로그인 ← "비로그인 상태에서 가입 신청을 누름" — P4-3)
```

### 7. 점검

```
"완성 조건" 체크리스트로 점검한다.
미달 항목이 있으면 해당 단계(1~6)로 돌아가 고친 뒤 다시 점검한다.
1층(3단계) 자체를 바꿔야 하는 문제가 나오면 스스로 바꾸지 않고, 8단계에서 유저에게 제안한다.
```

### 8. 전체 확인 — 유저 확인 2

```
트리 그림, 트리 밖 페이지 목록, 페이지별 섹션 목록, 이동 표를 한 번에 보여준다.
  - 아티팩트(웹 페이지) 발행이 가능한 환경이면 웹 페이지로 보여주고,
    불가하면 sitemap.md를 그대로 보여준다
  - 7단계에서 유저 판단이 필요한 것으로 남긴 항목이 있으면 함께 묻는다
유저의 수정을 반영하고, 반영 후 7단계 점검을 다시 통과시킨다.
유저가 확정하면 산출물을 쓰고 커밋한다.
```

## 다시 만들기 (추가 후보 반영)

```
R0. 후보 모으기
  사이트맵 재실행 대기 상태인 user-flow.md "사이트맵 대조 결과"와 wireframe.md "추가 후보"에서
  반영 방법이 "discovery-sitemap 재실행"이고 유저 결정이 반영인 줄을 모은다.
  후보마다 출처(user-flow F3 / wireframe P4)와 바꿀 곳(1층, 부모, 섹션 순서·나누기·합치기, 새 페이지)을 적는다.
  후보가 0건이면 다시 만들 것이 없다고 알리고 멈춘다.

R1. 영향받는 단계만 다시 한다
  1층이 바뀌는 후보 → 3단계(유저 확인 1)부터. 바뀐 1층 아래 페이지만 4~6단계를 다시 한다
  부모가 바뀌는 후보 → 4단계부터 그 페이지만
  섹션을 끼우거나 순서를 바꾸거나 나누거나 합치는 후보 → 5단계에서 그 페이지만
  모든 경우에 6단계 이동 표에서 바뀐 페이지의 들어오는 곳·나가는 곳을 다시 맞춘다
  바뀌지 않은 페이지는 손대지 않는다.

R2. 번호 지키기 (sitemap-guide.md "번호 규칙"의 다시 만들 때 규칙)
  - 남는 페이지·섹션의 번호는 그대로. 새 페이지는 가장 큰 번호 다음, 끼운 섹션은 소문자(P4-3a)
  - 순서를 바꾼 섹션은 번호가 섹션을 따라 움직인다
  - 합치거나 지운 번호는 취소선과 옮겨 간 곳을 남긴다
  - 번호를 다시 매겨야만 풀리는 후보가 있으면 스스로 매기지 않고 R3에서 유저에게 묻는다

R3. 점검과 확인
  7단계 점검을 그대로 한다. 추가로 "다시 만들기" 완성 조건을 확인한다.
  8단계 전체 확인에서는 전체 대신 바뀐 곳(바뀐 페이지, 새 번호, 취소선)과 반영한 후보 목록을 먼저 보여준다.
  확정되면 sitemap.md "재실행 기록"에 한 줄 남기고 커밋한다.

R4. 되돌려 보내기
  유저에게 순서를 안내한다:
    후보가 user-flow.md에서 왔으면 → discovery-user-flow `Resume: 6`
    후보가 wireframe.md에서 왔으면 → discovery-user-flow `Resume: 6` → discovery-wireframe `Resume: 5`
  user-flow.md와 wireframe.md는 이 스킬이 고치지 않는다 — 각 스킬이 재개하면서 바뀐 번호를 대조한다.
```

## 완성 조건

```
기능 배치:
  □ 입력 기능 목록의 모든 기능(핵심·보조)이 어느 페이지의 섹션에든 들어가 있다 (미배치 0)
  □ 기능 번호가 ui-spec의 번호와 일치한다 (새로 매긴 번호 없음)

페이지:
  □ 모든 페이지에 번호, 이름, 유형, 목적 한 줄이 있다
  □ 웹이면 모든 페이지에 URL 경로가 있다 (모달·드로어는 "—", 같은 경로가 두 번 나오는 곳 0)
  □ 목적을 한 줄로 쓸 수 없는 페이지가 없다 (목적 두 개인 페이지 0)
  □ 템플릿 페이지가 표시되어 있다
  □ 모든 페이지에 섹션 목록이 있다 (섹션이 비어 있는 페이지 0)
  □ 공통 섹션이 표시되어 있고, 공통 섹션 표에서 한 번만 정의되어 있다

구조:
  □ 1층이 3~5개다 (벗어나면 결정 기록에 이유가 있다)
  □ 1층끼리 목적이 겹치지 않는다
  □ 핵심 기능이 3층보다 깊이 있지 않다 (벗어나면 결정 기록에 이유가 있다)
  □ 트리 그림에 페이지를 가로지르는 이동이 그려져 있지 않다

이동:
  □ 뿌리를 제외한 모든 페이지에 들어오는 곳이 하나 이상 있다 (갈 수 없는 페이지 0)
  □ 트리 밖 페이지와 모달마다 그것을 부르는 행동이 적혀 있다
  □ 막다른 페이지가 없다 (나가는 곳이 비어 있는 페이지 0 — 1층 메뉴로 나가는 것도 포함)

과정과 언어:
  □ 유저 확인 두 번(1층 확정, 전체 확인)을 거쳤고, 결정 원문이 결정 기록에 있다
  □ 페이지·섹션 이름이 서비스 용어와 일치한다
  □ 경쟁사 자료를 참고한 곳에 출처(shots.md 파일명)가 있다
  □ 내부 용어·발명 조어 노출 0 (tone-guide 산출물 언어 규칙)

다시 만들기 (다시 만들기로 실행했을 때만):
  □ 기존 sitemap.md에 있던 번호 중 사라진 번호 0 (지운 것은 취소선으로 남아 있다)
  □ 기존 번호가 다른 페이지·섹션을 가리키게 된 곳 0
  □ 반영하기로 한 후보가 모두 반영되었고, 재실행 기록에 후보 수와 출처가 있다
  □ 바뀌지 않은 페이지의 섹션 목록이 기존과 같다

미달 시: 해당 단계로 돌아가 보완한다. 보완 불가하면
"최소 기준 미달: {항목} — {사유}" 경고를 sitemap.md 상단에 기록한다 (강제로 채우지 않는다).
```
