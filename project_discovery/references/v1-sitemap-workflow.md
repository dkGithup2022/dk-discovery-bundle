# Sitemap Workflow v1 — /dk-discovery-bundle:discovery-sitemap

> **이 동작은 에이전틱(agentic)한 동작이며, 두 지점에서 유저 확인을 받습니다.**
> 아래의 명령을 수행하되, 한 번의 생성으로 끝내지 마세요.
> "완성 조건" 체크리스트를 기준으로 스스로 점검하고,
> 미달 항목이 있으면 해당 단계로 돌아가 다시 수행하는 식으로,
> **완성될 때까지 반복적으로 LLM 호출(생성→점검→수정)을 이어가 답을 도출하세요.**
> 단, "유저 확인" 표시가 있는 두 지점(1층 확정, 전체 확인)에서는 유저의 결정을 대신 내리지 마세요.

확정된 기능 목록을 받아 **사이트맵**을 만든다: 서비스에 어떤 페이지가 있고, 어떻게 묶이고,
각 페이지가 위에서 아래로 어떤 섹션으로 이루어지고, 어느 페이지에서 어느 페이지로 갈 수 있는지.
산출물은 다음 단계인 유저 흐름과 와이어프레임의 직접 입력이 된다 — 두 단계 모두
이 문서의 페이지 번호로 페이지를 가리킨다.

## 참조 레퍼런스

```
You MUST read these before starting:
  sitemap-guide.md — 사이트맵의 정의, 모양, 페이지 유형, 섹션 목록, 이동 표, 번호 규칙
  tone-guide.md — 산출물 언어 규칙 (페이지 이름·섹션 이름·질문 문구 포함)
  git/git-verification.md — 커밋 규칙 (prefix discovery, 커밋 전 staged 파일 검증)

You MUST also look at the reference images before starting (Read 도구로 이미지를 연다):
  ${CLAUDE_PLUGIN_ROOT}/study/sitemap/flowmap_exameple.png
    — 페이지 칸마다 섹션을 위에서 아래 순서로 적는 방식, 칸에 붙은 상태 태그,
      트리에 속하지 않는 페이지를 "Add Separate Page"로 따로 두는 방식을 본다
  ${CLAUDE_PLUGIN_ROOT}/study/sitemap/yozum_example.png
    — 뿌리 → 1층 → 2층으로 내려가는 트리 모양, 로그인·가입·프로필을 트리 밖에 따로 둔 배치,
      사이트맵과 유저 흐름이 한 도구의 두 탭으로 나뉘어 있다는 점을 본다
이 이미지들은 산출물의 형식을 잡기 위한 참고다. 이미지 속 페이지 이름이나 구성을
우리 서비스의 내용으로 가져오지 않는다 — 내용은 항상 입력 문서에서 도출한다.
```

## 입력

```
필수:
  ui-spec/ui-spec.md — 기능 목록 (핵심 기능, 보조 기능, 각 기능의 출처)
    기능 번호는 이 문서의 번호를 그대로 쓴다. 새로 매기지 않는다.
  value-proposal/seed-v2.md — 고객군, 핵심 가치, 초기 공략 순서
선택 (있으면 참조 강도가 올라감):
  research/screenshots/*/shots.md, research/analysis/*.md — 경쟁사의 탭 구성과 페이지 구성
  hypothesize/hypotheses.md — Pass 2 니즈의 화면 위치 기록 (경쟁사가 이 기능을 어느 화면에 뒀는가)
```

## 진행 순서

### 0. 재료 읽기와 전제 확인

```
- 입력 문서를 모두 읽는다.
- 서비스 용어를 확인한다. ui-spec에 용어 표가 있으면 그대로 쓰고, 없으면 기능 목록에
  나오는 핵심 명사(예: 모임, 이벤트)를 추려 유저에게 확인한다 — 페이지 이름에 그대로 쓰이기 때문이다.
- 플랫폼을 확인한다: 앱 / 웹 / 둘 다. Platform: 인자나 seed-v2에 없으면 유저에게 묻는다.
  1층이 하단 탭이 될지 상단 메뉴가 될지가 여기서 갈린다.
```

### 1. 기능을 페이지로 묶기

```
기능을 "유저가 머무는 장소" 단위로 묶어 페이지 후보를 만든다.
  - 한 페이지에는 목적 하나만 둔다. 목적을 한 줄로 쓸 수 없으면 나눈다
  - 같은 틀로 여러 개 생기는 페이지는 템플릿 하나로 둔다
  - 보조 기능(로그인, 알림, 설정 등)도 빠짐없이 페이지 후보에 넣는다
각 페이지 후보에 목적 한 줄과 담는 기능 번호를 적는다.
```

### 2. 페이지 유형 나누기

```
각 페이지 후보에 유형을 붙인다: 탭 / 상세 / 모달 / 트리 밖 (sitemap-guide.md "페이지 유형")
트리 밖과 모달은 이 시점에 번호를 붙여 분리해 둔다 (X1…, M1…).
```

### 3. 1층(주 내비게이션) 정하기 — 유저 확인 1

```
핵심 가치와 고객군별 핵심 과업을 기준으로 1층을 3~5개 제안한다.
  - 1층마다: 이름, 목적 한 줄, 어느 고객군의 어떤 과업을 위한 것인지
  - 경쟁사 자료가 있으면: 경쟁사들의 탭 구성을 비교표로 함께 제시 (출처: shots.md 파일명)
  - 판단이 갈리면 구성이 다른 2안을 제시해 고르게 한다
유저가 확정하기 전에 4단계로 넘어가지 않는다.
  1층은 나머지 전체의 뼈대라서, 뒤에서 바뀌면 4~6단계를 전부 다시 해야 한다.
유저 결정 원문은 결정 기록에 보존한다.
```

### 4. 나머지 페이지를 트리에 매달기

```
탭이 아닌 페이지 각각의 부모를 정한다. 부모 = 그 페이지에 가장 주로 들어오는 곳.
확정된 페이지에 번호를 붙인다 (P1…). 트리 그림(mermaid)을 그린다.
페이지를 가로지르는 이동은 이 그림에 그리지 않는다 — 6단계의 이동 표에 적는다.
```

### 5. 페이지별 섹션 목록 쓰기

```
페이지마다 위에서 아래 순서로 섹션을 적는다.
  - 섹션마다: 이름, 담는 내용 한 줄, 담는 기능 번호
  - 여러 페이지에 반복되는 섹션(헤더, 하단 탭 등)은 [공통]으로 표시하고,
    "공통 섹션" 표에서 한 번만 정의한다
  - 경쟁사의 같은 성격 페이지가 있으면 그 섹션 구성을 참고로 붙인다 (출처 명시)
이 단계에서 모든 기능 번호가 어느 섹션에든 들어가야 한다.
```

### 6. 이동 표 쓰기

```
페이지마다 들어오는 곳과 나가는 곳을 적는다 (페이지 번호로).
트리의 부모→자식 이동도 포함한다 — 이 표가 이동의 전체 목록이다.
트리 밖 페이지와 모달은 어떤 행동이 그 페이지를 부르는지 함께 적는다
  (예: X1 로그인 ← "비로그인 상태에서 가입 신청을 누름" — P4-3)
```

### 7. 점검

```
"완성 조건" 체크리스트로 점검한다.
미달 항목이 있으면 해당 단계(1~6)로 돌아가 고친 뒤 다시 점검한다.
1층(3단계) 자체를 바꿔야 하는 문제가 나오면 스스로 바꾸지 않고, 8단계에서 유저에게 제안한다.
```

### 8. 전체 확인 — 유저 확인 2

```
트리 그림, 트리 밖 페이지 목록, 페이지별 섹션 목록, 이동 표를 한 번에 보여준다.
  - 아티팩트(웹 페이지) 발행이 가능한 환경이면 웹 페이지로 보여주고,
    불가하면 sitemap.md를 그대로 보여준다
  - 7단계에서 유저 판단이 필요한 것으로 남긴 항목이 있으면 함께 묻는다
유저의 수정을 반영하고, 반영 후 7단계 점검을 다시 통과시킨다.
유저가 확정하면 산출물을 쓰고 커밋한다.
```

## 완성 조건

```
기능 배치:
  □ 입력 기능 목록의 모든 기능(핵심·보조)이 어느 페이지의 섹션에든 들어가 있다 (미배치 0)
  □ 기능 번호가 ui-spec의 번호와 일치한다 (새로 매긴 번호 없음)

페이지:
  □ 모든 페이지에 번호, 이름, 유형, 목적 한 줄이 있다
  □ 목적을 한 줄로 쓸 수 없는 페이지가 없다 (목적 두 개인 페이지 0)
  □ 템플릿 페이지가 표시되어 있다
  □ 모든 페이지에 섹션 목록이 있다 (섹션이 비어 있는 페이지 0)
  □ 공통 섹션이 표시되어 있고, 공통 섹션 표에서 한 번만 정의되어 있다

구조:
  □ 1층이 3~5개다 (벗어나면 결정 기록에 이유가 있다)
  □ 1층끼리 목적이 겹치지 않는다
  □ 핵심 기능이 3층보다 깊이 있지 않다 (벗어나면 결정 기록에 이유가 있다)
  □ 트리 그림에 페이지를 가로지르는 이동이 그려져 있지 않다

이동:
  □ 뿌리를 제외한 모든 페이지에 들어오는 곳이 하나 이상 있다 (갈 수 없는 페이지 0)
  □ 트리 밖 페이지와 모달마다 그것을 부르는 행동이 적혀 있다
  □ 막다른 페이지가 없다 (나가는 곳이 비어 있는 페이지 0 — 1층 탭으로 나가는 것도 포함)

과정과 언어:
  □ 유저 확인 두 번(1층 확정, 전체 확인)을 거쳤고, 결정 원문이 결정 기록에 있다
  □ 페이지·섹션 이름이 서비스 용어와 일치한다
  □ 경쟁사 자료를 참고한 곳에 출처(shots.md 파일명)가 있다
  □ 내부 용어·발명 조어 노출 0 (tone-guide 산출물 언어 규칙)

미달 시: 해당 단계로 돌아가 보완한다. 보완 불가하면
"최소 기준 미달: {항목} — {사유}" 경고를 sitemap.md 상단에 기록한다 (강제로 채우지 않는다).
```
